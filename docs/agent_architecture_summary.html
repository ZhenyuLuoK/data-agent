§1 · Overview

这是一个怎样的 Agent

把"通用 LLM Agent"折弯为针对数据分析任务做了大量定向加固的工业级流水线。

⚠️

传统 ReAct 在 DABench 上的失效模式

单一 LLM ↔ Tools 自循环，"思考 + 调度 + 执行 + 终止"全揉在一段对话里

🌫 上下文涣散

长任务中对话不断膨胀，LLM 注意力被无关历史稀释。

🪤 漫游 / 跳步 / 漏做

没有显式分解，LLM 在多步任务中容易跳过中间环节。

💀 死循环 / 卡死

单 LLM 决定终止，没有外部预算与降级路径，task 撞 1800s 撞死。

设计思路演化

单 LLM ReAct → 识别 4 类失效 → 显式分解 + 角色解耦 → DAG + 路由器 + 同心预算 → 可调试可上限的工业流水线
🎯

本架构的解法：Plan–Schedule–Execute–Reflect 闭环

把"思考 / 调度 / 执行 / 审阅"四件事分给四种角色，把"流程推进"交给确定性代码

🧭

全局规划

一个 LLM 通看问题 + 真实数据画像，产出 DAG 计划。

⚙️

局部执行

另一个 LLM 在每个 DAG 节点的聚焦提示里推进、调工具。

🔍

最终审阅

第三个 LLM 检查答案的结构、单位、行列形态，决定 OK / RETRY。

🛡

控制流脚手架

调度器、重规划、失败处理、空轮纠偏，全部为纯代码节点。

§2 · Topology

9 类节点，4 大职责层

按"职责"把节点划成规划 / 调度 / 执行 / 监督降级四层；同层内的节点共享同一种"看待问题的视角"。

🧭

规划层 · Planning

决定"做什么"——把问题翻译成结构化 DAG。

LLM

planner

整张图的入口，每任务只跑一次。把"问题 + 数据集真实文件画像"翻译为 DAG 计划，包含若干带依赖关系的子任务节点和一个显式 final node。

输入：问题 + 文件画像　输出：PlanDAG
LLM

replanner

DAG 卡住或某节点彻底失败时进入。接收"上一份失败计划 + 状态 + 已有摘要 + 失败原因"，被要求产出一份避开同一失败模式的新 DAG。

关键差异：独立于 planner 存在 —— 失败信息和原始问题需要不同的提示与反思路径。
📋

调度层 · Scheduling

决定"现在做哪一个"——纯代码、零 LLM。

scheduler · 整张图的"心脏"

不调用 LLM，只做四件事：

Pure Control Flow
  1. ① 挑出"依赖已满足、状态 pending"的下一个就绪节点。
  2. ② 把目标 + 期望产物 + 上游依赖摘要拼成聚焦提示注入 executor。
  3. ③ 检查终止：全部完成 → reflector；卡住 → replanner。
  4. ④ 重置 per-node 步数计数器、刷新可视化。

设计动机：把"挑下一步做什么"从 LLM 责任里剥离，变成确定性逻辑。既消除 LLM 的"漫游 / 跳步 / 漏做"，又让上下文窗口始终精简。

🔧

执行层 · Execution

决定"具体怎么做"——绑定工具 + 真正接触世界。

LLM

executor

绑定全部数据分析工具的 ChatLLM。只看到聚焦提示 + 之前几轮对话，专注于当前一个 DAG 节点。

普通节点 → mark_node_done（带摘要）
最终节点 → answer（提交结果表）
让 LLM "用工具来宣布完成"——把推进权交还代码，避免 LLM 用自然语言模糊"暗示"完成。
CTL

tools · 标准 ToolNode

执行 executor 上一轮发出的工具调用，把结果以 ToolMessage 喂回。

🌍 这是整张图里唯一真正接触外部世界的节点（文件、SQL、Python 沙箱…）。
🛡

监督与降级层 · Supervision & Fallback

决定"出问题怎么办"——每一处可能陷入死循环的地方都有兜底。

LLM

reflector

在 executor 提交 answer 后触发。检查结构 / 列数 / 行数 / 单位 / 空值 / 字符串大小写。结论 OK 或 RETRY。重试有上限。

CTL

node_failure

节点超步预算后进入。做"软退避 vs 硬升级"二分：未到尝试上限 → 节点退回 pending（软重试）；超过 → 标 failed → 走 replanner。

CTL

nudge

应对某些模型偶发"既无文本也无工具调用"的空 AIMessage（实测 Qwen via DashScope）。提醒一次，不消耗节点步数预算。

END

finalize

no-op 叶子节点，唯一作用是把控制流接到 END。所有"放弃 / 通过 / 预算耗尽 / 反思满意"的路径都汇聚到这里。

Pipeline · DAG-driven, strict mode
   planner ──▶ scheduler ──▶ executor ──▶ tools ──┐
                  ▲     ▲           │ ▲                           │
                  │     │           │ └────── nudge ◀────────┤  (executor empty)
                  │     │           │                             │
                  │     │           │  (mark_node_done) ──────────┘
                  │     │           │
                  │     └───────────────────────────────── ◀ ─────┘
                  │                 │
                  │                 └─── (answer) ──▶ reflector ──▶ finalize ──▶ END
                  │                                    │
                  │                                    └─ (RETRY) ─▶ scheduler
                  │
                  └───── replanner ◀── (scheduler stuck / node_failure)
                              │
                              └─ replan_count ≥ max ─▶ finalize
§3 · State & Data Flow

两层状态：图状态 + 共享侧通道

对话归对话，控制状态归控制状态。把 DAG 的强类型状态从松散的消息流里独立出来，方便调度器/工具做精确判断，也方便事后导出结构化 trace。

💬

LangGraph 显式状态

AgentState

由 add_messages reducer 累加的对话流，外加几个轻量计数字段。

  • ▸对话消息流（系统提示 / 问题 / 聚焦提示 / AIMessage / ToolMessage / 软提醒）
  • ▸反思已用次数
  • ▸空轮纠偏已用次数
  • ▸当前节点已耗费的执行步数
  • ▸待重规划原因
  • ▸是否已最终化标志
🗂

共享侧通道

ToolRunContext / DAGRuntimeState

ToolNode 只能访问闭包里的对象，无法直接修改图状态——所以工具调用的副作用全部写到这里。

  • ▸DAG 本身（节点列表 + final_node_id）
  • ▸每个节点的状态（pending / in_progress / done / failed）
  • ▸每个节点的输出摘要（被 mark_node_done 写、被调度器读）
  • ▸每个节点的尝试次数
  • ▸当前焦点节点 ID / 重规划次数
  • ▸完整事件审计日志（trace 重建 + 可视化）
🔗

关键机制：上游摘要传递

整个架构里最重要的上下文工程决策之一。

调度器焦点新节点时，只会把该节点直接依赖的若干上游节点的"完成摘要"嵌进聚焦提示——不传完整对话历史、不传完整中间数据、不传 transitive 依赖。

🚫

不传全部历史

避免上下文爆炸；避免下游被无关细节干扰。

🚫

不传 transitive

间接依赖的关键信息已经在直接依赖的摘要里被显式总结过。

✅

传"摘要"而非原始数据

强迫上游显式命名 + 总结自己的产物，下游消费的是事实而非过程。

代价 & 补救：上游摘要质量直接决定下游成败，因此 prompt 强约束"摘要必须含具体路径/表名/数值"； 调度器还有启发式补救——如果上游摘要里看不到任何文件路径形态的 token，就额外提醒下游先调 list_context。

§4 · Control Flow

7 个路由器决定一切

LangGraph 的 conditional edges 让每个节点完成后都需由纯函数路由器决定下一站。 LLM 只决定"做什么内容"，不决定"下一步去哪"——这是整个 Agent 行为可预测、可调试、可设上限的根本原因。

①② planner / replanner 之后

无条件

→ 永远去 scheduler（规划完必走调度）。

③ scheduler 之后

4 选 1
  • 有重规划原因 → replanner（次数耗尽 → finalize）
  • 全部完成且已有答案 → reflector
  • 全部完成但无答案 → finalize
  • 正常焦点新节点 → executor

④ executor 之后

4 选 1
  • 有挂起工具调用 → tools
  • 空轮 + nudge 还有预算 → nudge
  • 空轮 + nudge 也耗尽 → finalize
  • 非空 + 节点步数耗尽 → node_failure

⑤ tools 之后

4 选 1
  • 刚调 answer 且答案就位 → reflector
  • 刚调 mark_node_done → scheduler
  • 都不是 + 当前节点步数耗尽 → node_failure
  • 否则 → executor（继续工作）

⑥ node_failure 之后

2 选 1
  • 还有重规划预算 → scheduler（软重试 / 走 replan）
  • 预算耗尽且确实有失败节点 → finalize

⑦ reflector 之后

2 选 1
  • OK → finalize
  • RETRY → scheduler（重新焦点最终节点）

⑧ nudge 之后

无条件

→ 直接回 executor（nudge 本身只是一段提醒，没有分支决策）。

💡

为什么这一切要落到代码里？

路由器的存在让整张图能在正常进展 / 软退避 / 硬升级 / 反思重试 / 重规划 / 终止之间精确切换。 下一步去哪由代码读"工具名 + 状态字段 + 计数器"决定，而不是 LLM 用自然语言"暗示"—— 所以才能给整个 Agent 设上限、能复现、能 debug。

§5 · Budget & Safety Net

四层同心圆预算

每一处可能"陷进去"的地方都有显式预算。从内到外形成四层同心保护——任何一个 LLM 失败都不能让整体卡死，每一层都要有明确的兜底路径。

①

单工具调用层

最内圈

检测连续 N 次相同参数的同一工具（典型死循环）和对同一份长文档过度分页（典型探索发散），在下一次 LLM 调用前注入一段一次性 SystemMessage 警告，引导模型换策略或提前提交。

检测：相同参数重复 检测：read_doc 过度分页 介入：软提醒
②

单节点层

两个独立维度

每个 DAG 节点都有 max_steps_per_node 个 executor 回合的预算；节点本身还有 max_node_attempts 次"整轮重试"机会。预算用尽 → 降级到 node_failure，进而升级到 replanner。

单节点回合数上限 单节点重试次数上限 介入：软重试 → replan
③

整体规划层

任务级

max_replans 限制整个任务最多被重新规划几次。一旦重规划次数耗尽且仍有节点 failed，整个任务直接 finalize（带失败原因）。

replan 次数上限 介入：失败收敛
④

整体反思层

最外圈

max_reflections 限制 reflector 最多让 executor 重交几次答案。防止 reflector ↔ executor 反复弹乒乓。

RETRY 次数上限 介入：强制 finalize
📐

额外的"动态节点步数上限"

不同形态的节点天然耗费不同步数——所以预算需要因节点而异。

  • ▸DAG 极简（≤2 节点）时，上限放宽到 1.5 倍——单节点天然要做更多事。
  • ▸依赖项多的节点，每多一个直接依赖增加固定额度——交叉引用上游天然更贵。
  • ▸最终节点再额外加少量额度——汇总 + 格式化通常需要更多 sanity check。
  • ▸最终结果 clamp 到 [base, 2×base]，防止 planner 出"病态 1 巨节点 DAG"绕过预算。
📜

这套同心圆是从一次惨痛事故里反推出来的

早期版本因为"双层重试叠加 + 无 timeout 上限 + 无步数上限"导致单 task 跑到 1800 秒撞死。 现在的同心预算、动态步数上限、按调用点差异化的重试策略，全都是从那次教训反推出来的—— 任何一个 LLM 失败都不能让整体卡死，每一层都要有明确的兜底路径。

§6 · Anti-Hallucination

前置数据画像 —— 让规划基于事实

planner 和 replanner 在被调用之前，都会先离线扫描任务的 context/ 目录，把真实文件清单、表名、文件头压成一份"数据集画像"，作为 HumanMessage 一并喂给规划 LLM。

❌

没有数据画像时

早期版本里，约 80% 的失败都是 planner / executor 虚构了不存在的文件路径。

  • ▸问题问"data.db 里的销售额"，但目录里其实只有 JSON。
  • ▸计划里写"读 Patient.json"，但文件其实在 json/ 子目录下。
  • ▸SQL 用了想象出来的表名，executor 只能在 no such table 里反复挣扎。
✅

注入数据画像后

规划阶段就看到"真实存在的文件清单 + 它们各自长什么样"，从源头压制路径幻觉。

  • ▸目录树（含子目录前缀）
  • ▸SQLite 库的真实表名 + CREATE TABLE 摘要
  • ▸JSON 文件头（前 ~400 字符）
  • ▸CSV 表头 + 前几行
  • ▸Markdown / TXT 文件头
🔄

replanner 也会拿一份最新的画像

因为很多时候重规划的根因就是"路径错了 / 表名错了"——必须基于事实重新出计划，而不是基于 LLM 的记忆。 画像作为"规划阶段的事实地基"，确保每一次出计划都能扎根在确定性的现实之上。

§7 · Case Studies

每一个节点背后，都站着一次真实的失败

所有看起来繁琐的节点、路由器、计数器，背后对应的几乎都是过往某次具体的失败模式。下面是 6 个最具代表性的"失败 → 架构补丁"对子。

Failure Pattern

① 路径 / 表名幻觉

早期版本里约 80% 的失败 都是 planner / executor 虚构了不存在的文件路径或表名—— 问"data.db 里的销售额"但目录里只有 JSON；写"读 Patient.json"但文件其实在 json/ 子目录下；SQL 用了想象出来的表名，executor 在 no such table 里反复挣扎。

📉 失败现场
FileNotFoundError: data.db no such table: customers Missing context asset: Patient.json
Architectural Patch

前置数据画像

planner 调用前先离线扫描 context/ 目录，拼一份紧凑画像：目录树 + SQLite 真实表名 + JSON/CSV 头 + 文档头，作为 HumanMessage 一并喂入。replanner 同样会拿一份最新画像。

✅ 修复后的 prompt 片段（示意）
Files under context/:
  [DIR ] json/
  [FILE] json/Patient.json (12,847 bytes)
  [FILE] doc/Laboratory.md (2,031 bytes)
File previews:
### json/Patient.json (json)
Head: { "patients": [{ "id": "P001", ...
Failure Pattern

② 重复参数 / 过度分页死循环

典型 task_80：executor 连续 4 次用完全相同的参数调 query_dataframe，烧掉 ~22 步预算却没拿到任何新信息。 另一种是 task_344 / 352 / 418：每轮变一点 offset / grep / slice 调 read_doc，但永远不收敛，8-12 次后被节点预算硬杀掉。

📉 失败模式
  • • 同一工具 + 同一参数 N 次 → "再调一次结果会不一样"幻觉
  • • 长文档过度分页 → 探索发散，不愿提交部分结果
Architectural Patch

单工具调用层软提醒

executor 节点在每次调用 LLM 前做两类检测：①连续 3 次相同参数同一工具；②4+ 次 read_doc。命中则注入一段一次性 SystemMessage，强制要求换策略或立即提交当前最佳部分结果。检测有"已经警告过则跳过"的去重逻辑，避免反复刷屏。

✅ 注入的提醒（节选）

"You have called query_dataframe with IDENTICAL arguments three turns in a row. Repeating will not return different data. You MUST (a) change at least one parameter, (b) switch to a different tool, or (c) stop exploring and call answer / mark_node_done with your best current result right now."

Failure Pattern

③ 节点超步、不愿提交

task_396 / task_418 之类的失败：executor 已经走到第 25 / 30 步还在用 execute_python 漫游探索，宁愿继续看代码也不愿调 mark_node_done / answer 提交"次优但能用"的结果。 上下文越来越长，最终被节点预算硬杀，整轮工作付之一炬。

📉 失败模式

"提交意愿不足"——LLM 把"还能再看一眼"误当作"还应该再看一眼"，错失提交时机。

Architectural Patch

步数预警 + 软重试 + replan 升级

  • ▸预警阶段：步数到达 70% 时注入"低预算"提醒，要求立即提交当前最好的结果。
  • ▸软重试：仍然超步则进 node_failure，节点退回 pending，重新焦点一次（让 executor 拿干净对话再来一次）。
  • ▸硬升级：累计尝试到上限 → 标 failed → 升级到 replanner，让另一个 LLM 视角换计划。
动态步数上限：依赖项多的节点 +3/dep；最终节点额外 +2；DAG ≤ 2 节点时 ×1.5。
Failure Pattern

④ 1800 秒超时撞死

最惨痛的事故：单 task 跑到 1800 秒撞死。根因是双层重试叠加——外层 5×、内层 2×、再 + 60s timeout，单次卡顿被放大成 (1+2)×(1+5)×60 ≈ 数百秒； 同时 client 端 timeout 异常被无脑重试，慢请求重试只会更慢，30s 累加成 90s。 后来又观察到：planner 失败 = 全死、executor 失败 = 由外层兜底、reflector 失败 = 完全无伤——三者重要性差 100×，却共享同一份重试预算。

Architectural Patch

差异化重试 + Timeout 不重试

调用点重要性重试次数
planner致命2
executor外层兜底0
reflector无伤0
  • ▸客户端 timeout 一律不重试（慢请求重试还是会慢）
  • ▸5xx / 429 才重试，且优先读 Retry-After 头
  • ▸OpenAI SDK 的 max_retries 强制设为 0，避免双层叠加
  • ▸四层同心圆预算从根上限制总调用数
Failure Pattern

⑤ 空 AIMessage 模型怪癖

实测 Qwen via DashScope 的 OpenAI 兼容端点，会偶发输出"既无 text 也无 tool_calls"的空 AIMessage——明明任务还远未完成，模型却"无话可说"。 如果直接当成"工作完成"会提前终止；如果当成"普通回合"则会消耗节点步数预算，几次空轮就把正常工具回合挤出预算。

📉 失败现场
AIMessage(content='', tool_calls=[]) ← 直接放过会终止 连续 3 次空轮 → 节点预算耗尽 → finalize
Architectural Patch

nudge 节点 + 步数豁免

  • ▸路由器检测到空轮且 nudge 还有预算 → 进 nudge 节点。
  • ▸nudge 注入一段明确提醒（"你必须要么调工具、要么提交完成"），然后直接回 executor。
  • ▸关键设计：空轮不消耗节点步数预算——它只是模型怪癖，不能让正常工具回合"被挤掉"。
  • ▸nudge 自身次数有上限（max_idle_nudges），超过则降级到 finalize。
💡 这是一个专门针对模型怪癖的轻量补丁层——隔离质量问题，不污染主流程预算。
Failure Pattern

⑥ "对了但格式错"的零分答

grader 是字节级比较 + 列签名匹配——所以下面这些"实际算对了的答案"会拿 0 分：

  • ▸金标 "52.17391304347826"，提交 "52.17"（被 round 了）
  • ▸金标 ""，提交 "None" / "NaN" / "<NA>"
  • ▸"how many X"问题，提交了 N 行明细而不是 1 行 COUNT
  • ▸金标 1 列，提交 4 列（多列被惩罚）
  • ▸日期 "March 1, 2024" 而不是 "2024-03-01"
Architectural Patch

reflector + RETRY 闭环

answer 提交后不直接finalize，而是先进 reflector：用独立 LLM 扫一遍 6 个维度（列数 / 行数 / 单位 / 空值 / 字符串大小写 / 数值精度）， 发现"对了但格式错"就发 RETRY: <一句话指令>，重置最终节点状态、回到 scheduler、让 executor 重交一次。

✅ RETRY 指令样例
RETRY: aggregate the result (COUNT/SUM/AVG) and submit one row RETRY: drop extra `id` and `description` columns to match the gold's 1-column shape RETRY: don't round; submit str(raw_value) for full precision
RETRY 次数受 max_reflections 上限保护，防止 reflector ↔ executor 弹乒乓。
§8 · Design Motives

五句话归纳设计动机

可以把这个架构的全部设计动机归纳成 5 句话——每一句都对应一类失败模式。

①

把规划与执行解耦

一个 LLM 通看全局产出 DAG，另一个 LLM 在每节点里只看局部聚焦提示。 同时缓解了"上下文过长 → 注意力涣散"和"多步任务 → 漏步跳步"两类问题。

②

把状态机从 LLM 手里拿走

推进 / 终止 / 重试 / 重规划全部交给纯函数路由器和工具触发，LLM 只通过 mark_node_done / answer 这种控制流工具来"申请"状态迁移， 不能用自然语言含糊地推进流程。

③

把"中间产物"从对话里抽出来变成显式摘要

每个节点用一段精炼摘要喂下游，而不是把整段历史、整张表都塞过去。 这是节点间协作能 scale 到 6 个子任务而不上下文爆炸的关键。

④

每一层都有降级路径

工具死循环 → 软提醒；节点超步 → 软重试；节点彻底失败 → replan；replan 用尽 → finalize。 整个图没有任何一个状态会陷在那里出不来。

⑤

数据先于推理

让 planner 在落笔前就看到真实文件画像，用确定性的事实压制 LLM 的幻觉倾向；让 reflector 在最终交付前再做一次结构性体检， 把"对了但格式错"的低级失败拦下来。事实在前，推理在后。

🔁

差异化重试

planner / executor / reflector 三种 LLM 调用对成败影响差 100×，配置不同的重试预算与退避策略；client timeout 一律不重试，5xx/429 才重试，并按 Retry-After 头精确退避。

🎬

DAG 实时可视化

每次 plan / replan / 节点状态变化、节点失败都触发一次 SVG 渲染（如配置了输出目录），让调试者能在事后回放整张 DAG 的演化过程。

📑

trace 与对话流分离

"对话消息（给 LLM 看）"与"步骤记录（给人和评测系统看）"在架构层面分开——后者从前者 + 事件日志重新组装，prompt 工程改变不会破坏 trace 兼容性。

§9 · vs Traditional ReAct

与传统 ReAct Agent 的关键差异

这套架构本质上是把"通用 LLM Agent"折弯成了一个针对数据分析任务深度加固的工业级流水线。

维度 传统 ReAct 本架构
任务分解 隐式（LLM 自己边想边做） 显式（planner 先产出 DAG）
状态推进 LLM 用自然语言决定何时停 工具调用 + 路由器决定
上下文 单条不断膨胀的对话 每节点局部聚焦提示 + 上游摘要
失败恢复 通常无 三层（节点软重试 / replan / 反思 RETRY）
预算控制 通常单一 max_steps 节点级 / 任务级 / 反思级 / 重规划级四层独立
抗幻觉 依赖 prompt 前置数据画像 + reflector 后置审阅
可观测性 仅消息流 消息流 + DAG 事件流 + DAG 实时 SVG
"

所有看起来繁琐的节点、路由器、计数器，背后对应的几乎都是过往某次具体的失败模式。

— 这就是从 ReAct 到 LangGraph DAG Agent 的演化全部意义所在。
