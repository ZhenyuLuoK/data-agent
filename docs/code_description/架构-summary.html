Problem & Insight

为什么需要这套架构？

理解 boost-agent 的所有设计取舍，必须先理解评测平台对 Agent 加的四条硬约束。

! 四条评测硬约束

📊
打分规则：列签名集合匹配

忽略列名与列顺序，但对多余列施加线性惩罚。 Score = max(0, Recall − λ × extra/predicted)

⇒ "多答列" / "漏答列" / "格式错位" 都直接扣分；"列名漂移" 不扣分。

⏱️
运行时预算：硬性 timeout 包裹

外层 timeout 套整个容器，到时先 SIGTERM 后 SIGKILL，进程随时可能被强行收尾。

⇒ "保底文件必须在任意瞬间存在"，不能依赖跑完后统一拷贝。

📁
目录契约：固定路径 + 单一文件名

评测平台只挂载固定输入 / 输出路径，且只读输出路径下一个特定文件名的答案文件。

⇒ 多轮投票的中间候选不能"污染"评测路径。

🌐
运行期不可联网

除调用 MODEL_API_URL 外，镜像内不允许任何对外网络访问，否则按违规处理。

⇒ API Key 不落镜像、运行期清空 pip 镜像源。

🧩

🛡️

💾

Layered Architecture

六层分层架构

每一层只负责一个明确职责，层与层之间通过明确契约解耦——目录结构、文件名约定、不可变状态字段、强校验工具签名。

分层视图
┌─────────────────────────┐ │ Docker Entrypoint 接入层│ ← 评测平台 ├─────────────────────────┤ │ CLI / 配置层 │ ├─────────────────────────┤ │ 数据集层 │ ├─────────────────────────┤ │ 运行调度层 │ │ Runner / Vote / Retry / │ │ Score │ ├─────────────────────────┤ │ Agent 核心层 │ │ LangGraph DAG (9 节点) │ ├─────────────────────────┤ │ 工具层 (12 工具 / 4 类) │ └─────────────────────────┘
数据流自上而下；调度层是核心枢纽，向上对接 CLI、向下编排 Agent。

① Docker / Entrypoint 接入层

边界层

评测平台契约的唯一对接点。后台周期性原子拷贝保底文件到评测目录、屏蔽多轮中间产物、信号 trap 收尾。Runner 与评测路径完全解耦。

② CLI / 配置层

入口层

命令分发统一入口；YAML + 环境变量展开（API Key 不落镜像）；不可变配置对象向下传递；轻命令懒加载、快速启动。

③ 数据集层

契约层

题目目录索引；"上下文目录路径"是整个工具沙箱的根；不可变 Schema 跨层传递；字段漂移立刻 fail-fast；稳定排序便于回归对比。

④ 运行调度层（Runner / Vote / Retry / Score）

编排层

每题一进程隔离 + 硬超时；多轮调度遵循"保底文件契约"；签名规范化投票；失败重试 Pass；本地 self-eval。把模型随机性压成可投票的多份候选。

⑤ Agent 核心层（LangGraph DAG）

推理层

9 节点状态机：Planner / Scheduler / Executor / Tools / Reflector / Replanner / NodeFailure / Nudge / Finalize。双通道状态架构（messages 主通道 + ToolRunContext 侧通道）。

⑥ 工具层

能力层

四类角色：文件类 / 探索类 / 计算类 / 控制流类。统一受路径沙箱保护（路径逃逸阻断 + 缺失文件友好提示）。强 schema 输入。

Agent Core · LangGraph DAG

推理骨架：9 节点状态机

把 ReAct 单循环重构成多节点协作的有限状态机：每个节点只看自己的 goal 与上游事实摘要，避免长上下文中迷失。

🎯 主流程节点

4
Planner 规划器

题目入口，仅运行一次。注入 Dataset Profile 后产出结构化子任务 DAG。

Scheduler 调度器

挑选下一个 ready 节点，构造 Focused Prompt（只含上游事实摘要）。

Executor 执行器

在当前聚焦节点内调 LLM，决定调工具 / 写文本 / 结束当前节点。

Tools 工具节点

实际执行工具调用；副作用通过返回值或侧通道写入。

✅ 校验 / 终止节点

2
Reflector 反思器

提交最终答案后做四维校验（结构 / 冗余列 / 聚合 / 格式），输出 OK 或 RETRY。

Finalize 终止节点

触发整张图的退出，是 END 之前的唯一占位节点。

💡 Reflector 的 RETRY 不回到 Executor，而是回到 Scheduler 重新聚焦终节点，复用统一入口避免状态错乱。

🛡️ 兜底节点

3
Replanner 重规划

原 DAG 无法继续推进时触发；吃前一版计划 + 失败原因，重新出 DAG。

NodeFailure 节点级兜底

单节点步数耗尽时触发；软重试当前节点或上抛触发 Replan。

Nudge 轻量唤醒

执行器返回空响应时触发，注入简短提示让 LLM 重新发声。

DAG 路由关系（条件路由）
┌──────────────────────────────┐ ▼ │ START → Planner → Scheduler → Executor → Tools ──────────────┤ ▲ │ │ ▲ │ │ │ │ └── Nudge ◀────(空响应)───┤ │ │ │ │ │ │ └── (提交 answer) → Reflector │ │ │ │ │ ├─ OK → Finalize → END │ │ └─ RETRY → Scheduler │ │ │ └── 无 ready 节点 / 节点失败 → NodeFailure → Scheduler │ │ │ ▼ │ （重试预算耗尽？） │ │ │ ▼ └─────────────────────── Replanner ────────────┘ （Replan 预算耗尽 → Finalize → END）
Tools 路由分流

调"提交答案" → Reflector；调"标记节点完成" → Scheduler；调普通数据工具 → Executor。

RETRY 路径

Reflector 的 RETRY 走 Scheduler 而非 Executor，复用"清空当前节点状态再进入"的统一入口。

两层兜底

NodeFailure 是节点级软重试；Replanner 是计划级重写。前者优先，后者兜底。

🔀 双通道状态架构

LangGraph 原生 messages 通道无法承载"标记节点完成 / 提交最终答案"这类控制流副作用。架构层面引入第二条通道 ToolRunContext，把消息流与控制流彻底分离。

主通道

messages（LLM 对话流）

  • • HumanMessage · 用户 / Scheduler 注入
  • • AIMessage · LLM 输出
  • • ToolMessage · 工具结果回传

由 reducer 自动追加，不可绕过。

侧通道

ToolRunContext（DAG 状态 / 控制流）

  • • DAG 拓扑 + 节点状态
  • • 节点输出摘要（事实事实）
  • • 最终答案对象
  • • 历史所有提交答案（可回溯）

per-task 隔离；控制流工具直接读写。

per-task 隔离

每题独立 context；任意两题状态完全隔离。

强校验入口

控制流工具入参严格校验；非法尝试立刻打回。

下一拍可感知

无需事件总线；scheduler 下次执行就能看到新状态。

五大子机制 · 让 DAG 工作的关键设计

从反幻觉到自我保护，每一个子机制都对应一类历史回归经验

Dataset Profile · 反幻觉的核心

实测中最大的失败模式：模型凭空捏造文件路径（题目说有 sqlite，模型直接读 data.db，但真实文件叫 db/main.sqlite）。

解决方案：规划前注入真实文件清单
  • • 真实存在的目录与文件清单（含路径与大小）
  • • 每个 SQLite 文件的全部表结构
  • • 每个文档 / CSV / JSON 的头部样本
  • • Prompt 中强制要求："只允许引用 profile 中出现的文件"

⇒ 把"反幻觉"从"提示词约束"升级为"模型根本看不到不存在的路径"的结构性保证。

Files under context/: [DIR ] db/ [FILE] db/main.sqlite (45123 bytes) [FILE] doc/Laboratory.md (8201 bytes) File previews: db/main.sqlite (sqlite, 3 tables; pass exactly `db/main.sqlite`): - table `patients`: ... - table `labs`: ... - table `visits`: ... doc/Laboratory.md (text): Head: # Laboratory Reference ...

Focused Prompt · 长上下文压缩

DAG 各节点之间不直接共享对话历史。每次 Scheduler 选中一个节点时，构造的"聚焦提示"只包含：

✅ 进入 LLM 输入
  • • 当前节点的 goal 与期望输出
  • • 上游节点的 1-3 句事实摘要
  • • 控制流工具调用建议
❌ 不进入 LLM 输入
  • • 上游节点的工具调用日志
  • • 上游节点的中间消息历史
  • • 上游节点的失败重试记录

⇒ 把"长上下文 ReAct"变成"短上下文焦点接力"，让一道题的总 token 消耗保持在可控范围，模型在每个节点都"轻装上阵"。

Executor 三层自我保护

执行器位于 LLM 自由度最高的位置。为防止常见失败模式吃光预算，外面包了三层观测器 + 一个特殊补丁：

🔁 重复调用检测

连续几轮用完全相同参数调同一工具时，注入强提示让模型立刻提交当前结果或更换工具/参数。

📄 长文档过用检测

连续多次调用文档读取工具（哪怕参数不同）时，建议改用列目录、受限 Python 或直接结束当前节点。

⏰ 步数预算软警告

节点内步数接近上限时注入"立刻提交当前结果，哪怕是部分答案"的提示。

💨 空响应不计步

LLM 偶发返回空内容时不计入步数预算，由 Nudge 节点低成本恢复，避免几次空响应就把节点预算耗光。

⇒ 这一层是"LLM 自由度"与"硬约束"之间的中间层防护，把模型的常见反模式拦截在它造成实质损失前。

差异化 LLM 重试策略

所有 LLM 调用走同一统一入口，但按调用点采用不同的重试 profile。底层 SDK 内置重试被显式关闭，避免双层叠加。

调用点 重试策略 设计依据
Planner 多次重试 + 指数退避 失败将导致整个 task 死，必须给重试机会
Executor 不重试 失败有节点级 / 计划级 / 投票级多层外层兜底
Reflector 不重试 反思失败不影响保底答案（已写出），损失可承受
429 速率限制 读 Retry-After 头 + 长退避上限 速率限制有标准协议，遵守即可
客户端超时 一律不重试 超时多半源于模型本身慢，重试只会再超时

Reflector 的四维语义校验

Reflector 不是简单的存在性检查，而是直接对应评分公式的四个惩罚维度。让"评分公式"从"线上一次性的黑盒"变成"线下可前置的检查项"。

六条设计动机

1

压缩 step 数

高信息密度工具：列画像替代 head/dtypes/shape 三连击；文档读取内置 grep 模式；DataFrame SQL 替代 pandas group_by。

2

沙箱双层防御

路径逃逸阻断（拒绝 .. 与符号链接）+ 缺失文件友好提示（附带真实目录清单）。

3

错误即修正信号

异常类型 + 原文直接转工具消息回传，富错误信息驱动模型自修正，省一轮"应该读哪个文件"的反问。

4

强 schema 输入

所有工具用结构化 schema 声明参数，LLM 拿到显式字段定义，从源头降低参数错传概率。

5

控制流强校验

DAG 必须存在 / 节点 ID 有效 / 是当前聚焦节点 / 答案行长自洽。任一不满足立刻打回，避免"看似成功实则状态错乱"。

6

受限 Python 硬边界

硬性时间上限 + 工作目录强锁 + stdout 捕获。不是为了沙箱安全，而是为了预算可控。

🔧

备份引擎：Legacy ReAct 路径

工具层同时保留了一套老式 ReAct 工具注册表作为备份引擎：当主路径（LangGraph DAG）出现致命问题时，调度层可以显式注入 model + tools，切回单循环 ReAct 模式跑同一道题。

这是"双引擎"架构选择——主引擎追求最优能力，备份引擎追求最低假设、最简实现，能跑出答案就比卡住强。
Runner · Vote · Retry · Score

运行调度层：把随机性压成多数决

Agent 单次输出存在天然随机性。调度层的使命是把这种随机性压成可投票的多份候选，再用规范化签名做多数决。

🔒

5.1 隔离执行：每题一进程

每道题以独立子进程运行，受硬性时间预算保护。这是线程模型无法做到的：

🐛
C 扩展卡死

SSL 握手等纯 C 代码里 KeyboardInterrupt 失效。

⚔️
SIGTERM → SIGKILL

先软杀宽限期内退出，否则硬杀强制收尸。

💥
崩溃可捕获

OOM / 段错误 → 退出码 → failure_reason，不挂全局。

两条执行路径
  • • 默认路径：子进程隔离 + 硬超时 + 跑 LangGraph DAG（多题并发的正式运行）
  • • 进程内路径：显式注入 model + tools 时直接在当前进程跑（Legacy ReAct / 调试 / 单测）；并发自动压到 1，避免 LLM 客户端线程不安全

5.2 多轮调度与"保底文件"契约

每道题独立跑多轮，每一轮都尝试给出一份候选答案。文件命名规则严格遵循以下契约：

阶段 该轮该题的输出文件名 语义
第 1 轮 prediction.csv（保底文件） 永远写保底文件
第 N 轮（N≥2），保底已存在 rN.csv（候选文件） 仅参与投票，不暴露给评测
第 N 轮（N≥2），保底仍不存在 prediction.csv（补位） 前面所有轮失败，本轮补位救场
🔑 关键不变量

保底文件代表"当前最佳"。容器外同步守护进程只看保底文件——只要它存在就有保底分。投票胜者通过原子覆盖把保底文件升级为更优答案。

⚠️ 并发安全的微妙之处

候选文件名规则必须在主线程提交任务时就预先确定。否则同一轮多个 worker 同时启动都会看到"保底不存在"全都补位互相覆盖。

5.3 / 5.4 投票域签名规范化与裁决规则

🔢 列签名集合化

columns = [c1, c2, c3] rows = [[a, b, c], [d, e, f], ...] # 第 1 步：每列单元格规范化 + 排序 # （行无序） col_sigs = [ sorted([norm(a), norm(d), ...]), sorted([norm(b), norm(e), ...]), sorted([norm(c), norm(f), ...]), ] # 第 2 步：所有列再排序 # （列无序，列名也不参与） signature = sorted(col_sigs)
⇒ 两份答案签名相等当且仅当它们用列签名匹配方式打分会得到相同结果。

1-2

单元格规范化规则（按优先级）
① null 字面量（None / "null" / "nan" / "NaT"）→ 统一为空字符串
② 布尔值 → "True" / "False"（不冒充数字 1.0 / 0.0）
③ 数字 → 按固定精度四舍五入（合并近似答案）
④ ISO / 零填充日期 → 统一格式
⑤ 长形式英文日期（"March 1, 2024"）→ ISO 化
⑥ 其他文本 → strip + 去 \r\n
⚠️ 歧义日期（US MM/DD vs EU DD/MM）→ 一律不动，避免静默换月日

5.5 双归一化：投票域 vs 评测域分离

签名规范化在系统中有两套独立实现，分别服务于不同目的。两者不混用、不共享代码——这是有意的架构隔离。

投票域

激进归一化

  • ✓ 数字精度统一
  • ✓ 日期格式统一
  • ✓ 长文本归一
目的：最大化候选合并能力

让"看似不同实则同义"的答案合并以提高投票聚合能力

评测域（本地 self-eval）

保守归一化

  • ✓ 仅 strip 空白
  • ✓ 少数 null 字面量
  • ✗ 不做精度 / 日期归一
目的：贴合真实评测器行为

让本地分数尽量贴近线上真实分，避免本地虚高

5.6 落盘前的最终规范化

投票胜者覆盖保底文件后，调度层还会对最终保底文件做一次规范化重写——把每个单元格走一遍投票域归一化函数后写回。这是"评测系统看到的字节"层最后的格式统一。

5.7 失败重试 Pass

所有投票轮跑完后，对仍失败的题目再单独跑一次。这一设计的关键：重试发生在投票之后。投票本身已经能挽救一部分波动型失败，剩下仍失败的多半是稳定型失败。

✓ 重试成功

用原子重命名把临时产物提升为正式答案，trace 同样升级。

✗ 重试失败

删除临时产物，原本失败状态保持不变。不会让重试反而把状态搞乱。

5.8 可观测性维度

  • • 每题每轮完整 trace（思考 / 动作 / 观测）
  • • 每题投票摘要（候选状态 / 签名 / 应用规则）
  • • 全 run 总结（轮次 / 重试 / 投票统计）
  • • 本地评分报告
💡 候选状态字段（ok / missing / empty / unparseable）是纯可观测性字段，不参与投票裁决，纯粹用于事后定位"为什么某轮全军覆没"——观测面与控制面严格分离。

5.9 本地 Self-Eval：评分层

独立的本地评分组件，按照评测平台的评分规则对每题打分（召回率减去多余列惩罚），落出每题分数与汇总统计。

与投票域归一化函数刻意分离——评测域必须保守。这是"线下回归测试"的基石，让任何代码改动都能立刻量化对得分的影响。

CLI · Dataset · Entrypoint

边界三层：合规、契约与稳定接入

CLI/配置层负责合规与可切换；数据集层守护沙箱根契约；Entrypoint 层把"评测平台契约"与"Runner 内部语义"彻底解耦。

⌨️

六、CLI / 配置层

命令行入口统一、配置环境变量展开、不可变配置对象、懒加载策略——四个机制共同保证"合规 + 可切换 + 快速调试"。

关键机制
  • • 命令分发统一入口：状态查看 / 单题元数据 / 单题运行 / 整集运行 / 本地评分
  • • 配置环境变量展开：模型名 / API 地址 / API Key 通过环境变量注入；YAML 中以占位符声明（含默认值）
  • • 不可变配置对象：加载后冻结，跨层不可变；天然线程/进程安全
  • • 路径解析约定：相对路径以项目根为基准；绝对路径直接保留
  • • 三套配置分场景：示例 / 本地开发 / 提交镜像
  • • 懒加载策略：轻命令瞬时启动，重依赖按需加载
  • • 配置项校验前置：投票轮数等关键字段在加载阶段就校验
设计动机与优点
  • • 合规要求：API Key 不落镜像、运行期不联网（除模型 API 外）是参赛硬约束
  • • 无缝切换：同一份代码通过切换配置就能在本地冒烟与提交镜像之间切换
  • • 快慢分离：高频轻命令几乎瞬时启动，不会被 Agent 链路拖慢
  • • 快速失败：配置不合法立刻报错；任何字段名漂移立刻可见
📚

七、数据集层

数据集层守护两个核心不变量："上下文目录路径"是整个工具沙箱的根，不可变 Schema 跨层传递不会被意外修改。

目录契约固定

🔒
不可变 Schema

题目记录 / 资产 / 答案表格全部 frozen

⚡
快速失败

字段名漂移立刻报错

🔢
稳定排序

按编号整数排，不是字典序

🎚️
筛选能力

按题号 / 难度白名单

💡 为什么"路径不变量"是基石：所有工具都假设路径相对于上下文目录解析；这个不变量一旦被打破，路径沙箱就形同虚设。把"上下文路径"集中在一处定义，让沙箱只有一个被信任的入口。
🐳

八、Docker / Entrypoint 接入层

三个矛盾需求的统一解

接入层要同时满足三个看似矛盾的需求：

需求 ①

多轮投票需要把候选文件互相隔离——不能让评测看到中间候选。

需求 ②

评测平台只看一个固定路径——不知道运行 ID。

需求 ③

进程随时可能被强杀——不能依赖"跑完后统一拷贝"。

三方案对比

方案 缺点 结论
Runner 直接写评测路径 候选文件都暴露给评测，违反"只读保底文件"语义；中间状态被评测看到 ❌ 弃用
跑完后再统一拷贝 一旦被强杀，所有未拷贝答案丢失 ❌ 弃用
后台同步 + 隔离目录 无明显缺点；轮询频率远低于平台杀进程的宽限期，损失被压在很小窗口内 ✅ 采用

第三方案的具体落地

  • ① Runner 仍写到带运行 ID 的子目录隔离多轮产物；
  • ② 后台进程按固定周期原子拷贝保底文件到评测路径；
  • ③ 第 1 轮一旦写出保底文件，几秒内就同步到评测路径，就算后续被强杀也已经有保底答案；
  • ④ 多轮投票胜者覆盖隔离目录的保底文件后，下一个同步周期把胜者拍上去；
  • ⑤ 候选文件永远不会出现在评测目录，符合"只读保底文件"。

其他关键机制

🪝 信号收尾 trap

收到终止信号时做最后一次同步再退出

🌐 清空依赖镜像源

构建期加速，运行期清空避免隐式联网违规

🔐 环境变量自检不泄漏

只打印 set/unset，绝不打印 Key 本身

📅 不预创建运行目录

Runner 自己生成时间戳目录，避免撞目录

🔌 评测对接零侵入

Runner 不需知道"评测看哪个路径"，对接完全在 entrypoint 完成

💪 强壮性极高

无论平台何时发什么信号，都有合规答案保底

📋 合规审计友好

日志无 Key、运行期无联网、构建/运行网络配置严格分离

Phase 1
启动 + 第 1 轮

entrypoint 启动后台同步守护，dabench 加载配置、索引数据集，第 1 轮并行跑所有题落保底文件，几秒内同步到评测路径。

Phase 2
第 2、3 轮投票

候选文件隔离写出（保底文件不动）；保底文件不存在时补位。所有候选文件名在主线程提交时预先确定，避免并发竞态。

Phase 3
Retry Pass

投票之后对仍失败的题再单独跑一次。成功则原子重命名提升为保底，失败则丢弃临时产物保持原状。

Phase 4
全表投票 + 收尾

签名规范化 → 多数决 / earliest → 胜者原子覆盖保底文件 → 落最终规范化 → 落总结。trap 做最后一次同步后退出。

每一层只做自己的事，层与层之间通过明确的契约（目录结构、文件名约定、不可变状态字段、强校验工具签名）解耦，可以独立替换或调整。

Design Philosophy

设计哲学：五条核心原则

把分散在各层的设计取舍归纳为五条可独立验证的原则。任意一条违反，整个架构的优势都会打折。

1

DAG 驱动，反长上下文

把"长对话"切成"短焦点"，每个节点只看自己需要的事实，从根上避免模型迷失。

  • • Dataset Profile → 规划只能引用真实路径
  • • Focused Prompt → 节点之间只透传事实摘要
  • • 三层自我保护 → 拦截模型常见反模式
2

保底语义优先于最优语义

宁可先落一份合规答案再优化，绝不接受"算到最好但没落盘"。多轮、投票、重试都建立在保底之上做加法。

  • • 任何阶段崩溃都至少留下保底答案
  • • 后续轮的胜者通过原子覆盖升级保底
  • • 绝不会让结果变更糟（monotonic 改进）
3

失败的爆炸半径要可控

工具失败 → 节点重试 → 计划 Replan → 反思 RETRY → 多轮投票 → 单题救援，每一层都有有限上限。

  • • 避免无限烧预算
  • • LLM 重试按调用点差异化
  • • 底层 SDK 内置重试被显式关闭，避免双层叠加
4

控制流必须显式且强校验

节点完成、答案提交都做成专门的工具与状态字段，不依赖 LLM 自由文本。

  • • 控制流走 ToolRunContext 侧通道
  • • 与 messages 主通道严格分离
  • • 任何不合规尝试立刻打回成工具错误
5

投票域与评测域不混用

归一化在不同目的下用不同强度——投票域激进合并、评测域保守贴合，两套独立实现互不共享代码，避免"本地高分线上崩"。

投票域（激进）

让"看似不同实则同义"的答案合并以提高聚合能力

评测域（保守）

贴合真实评测器行为，避免本地虚高

💡 可观测性字段（如候选状态）也与控制流字段严格分离，避免"日志变成隐式控制流"的反模式。

总结

在模型本身存在随机性、评测平台存在硬时间预算、任何深层调用都可能卡死的现实约束下，
系统仍能给出 稳定、可解释、可调试、可恢复 的答案。

三个关键架构选择

📦

结构化而非纯文本

所有产物都是 JSON / SVG，可程序化二次处理。让"调试"从"猜测式手动复现"变成结构化分析。

🔀

与控制流隔离

观测字段不参与控制流裁决（如候选状态字段不参与投票），避免"日志变成隐式控制流"的反模式。

💾

不依赖外部存储

所有产物都落在隔离的运行目录下，离线可查、离线可对比，无需任何外部服务。

Key Insights & Takeaways

关键洞察与启示

从 boost-agent 的架构设计中可以提炼出四个维度的可迁移经验，适用于其他需要在硬约束下跑 LLM Agent 的场景。

🧭

设计哲学

  • ▸ 保底先于最优：永远先有一份合规答案落盘，再做任何优化。
  • ▸ 失败爆炸半径可控：每一层失败兜底都有有限上限。
  • ▸ 显式优于隐式：控制流走专门工具，不依赖 LLM 自由文本。
  • ▸ 关注分离：投票域 vs 评测域、可观测性面 vs 控制面。
⚙️

技术创新

  • ▸ 双通道状态架构：messages + ToolRunContext 把对话流与控制流彻底分离。
  • ▸ Dataset Profile 反幻觉：从"提示词约束"升级为"结构性保证"。
  • ▸ Focused Prompt 接力：用上游事实摘要替代完整对话历史。
  • ▸ 列签名规范化投票：忽略列序 / 行序 / 列名，按集合多数决。
🚀

实践启示

  • ▸ 子进程隔离：在 LLM 调用栈可能卡死的场景下，比线程更可靠。
  • ▸ 差异化重试：按调用点决定是否重试，避免双层叠加放大卡顿。
  • ▸ 原子覆盖 + 后台同步：解耦 Runner 与评测平台契约的通用模式。
  • ▸ 错误即修正信号：把工具失败当作驱动 LLM 自修正的输入。
🔭

局限与未来工作

  • ▸ 投票候选数量上限：当前 ≤ 3 票，更多候选下的 tiebreak 策略待探索。
  • ▸ Reflector 是 LLM 校验：本身可能误判；可考虑引入硬规则前置。
  • ▸ DAG 由 Planner 一次画死：执行中无法增量调整，依赖 Replan 兜底。
  • ▸ 子进程开销：每题独立进程对小题目存在固定启动成本。
💡

分层 + 兜底 + 保底 + 隔离 是把 LLM Agent 从'实验室能跑'推向'生产可用'的核心范式。"
