DAG 编排 · 多轮投票 · 失败自愈

Problem & Insight

为什么是 DAG + 投票，而不是更大的 ReAct？

从评测约束反推，单一 ReAct 循环在三条曲线上同时输给了多节点 + 多候选架构。

⏱️

硬性时间窗

A 榜 7200s · B 榜 12h，外层 timeout --kill-after=30s，超时直接 SIGKILL。

📐

列签名 + 冗余惩罚

评分 Score = max(0, Recall − 0.5·extra/predicted)。多一列就扣 0.5/N，正确答案 +1 列也只剩 0.5。

🚫

禁止运行期联网

除调用 MODEL_API_URL 外不得联网，API key 必须从 ${"{"}VAR{"}"} 注入，硬编码即违规。

❌ Naive ReAct 在这套约束下的三个崩溃模式

长上下文迷失

Step 20+ 后模型反复 read_doc 同一文件、忘记已读结果。task_344/352/418 都因此把 step 预算耗光。

幻觉路径

~80% 的失败是模型猜路径——题里有 sqlite，模型去读 data.db，但实际只有 db/main.sqlite，连环 FileNotFoundError。

单次随机性

temperature=0.5 仍偶发抽风：分组遗漏、列名漂移、整数当浮点。一次抽样就交卷 = 把概率全押一个回合。

✅ 三层组合拳：每一层都精准击中一种崩溃

🧩

DAG 切分 + 焦点提示

planner 把任务拆成 2-6 节点；executor 一次只看 当前节点 goal + 上游 1-3 句 summary，把上下文从"几十轮日志"压缩到"几百字符"。

🛡️

Dataset Profile 强约束

planner 调用前注入真实文件清单 + sqlite schema + json/csv head，prompt 强制"只引用 profile 里的文件"，幻觉路径直接归零。

🎲

多候选签名投票

同一题跑 3 轮 → 列签名规范化 → 多数票胜出。把"单次抽样"换成"3 次独立 i.i.d 实验"，正确率随轮数指数级靠近 1。

🧠 LangGraph DAG 流水线（9 节点）

每个节点的职责在 _build_graph() 内通过 StateGraph(AgentState) 拼接。条件路由由 9 个 route_after_* 函数控制。

1

planner

注入 _build_dataset_profile 真实文件清单，输出 2-6 节点 JSON DAG。每 task 仅 1 次（除非 replan）。

2

replanner

scheduler 卡住或节点 attempts 用尽时触发，吃失败原因重画 DAG。max_replans=2。

3

dag_scheduler

drain 完成信号 → 选 ready 节点 → 注入 focused prompt（goal + 上游 summaries）。

4

executor

ChatOpenAI + bind_tools。三层保护：identical args 检测 / read_doc 过用检测 / 步预算软警告。

5

tools (ToolNode)

LangGraph 标准节点。错误以 {"{type(exc).__name__}: {exc}"} 透传，让模型自我修正。

6

nudge

executor 空响应（Qwen 偶发）时注入"请继续"提示。max_idle_nudges=2。

7

node_failure

节点 step 用尽时增 attempts；未到上限软重试，到上限 mark failed 并触发 replan。

8

reflector

校验 answer 表的列数、行数、聚合是否匹配题面。输出 OK 或 RETRY: ...。

9

finalize

空节点占位，存在的意义只是接 add_edge("finalize", END)。

AgentState (TypedDict)
class AgentState(TypedDict, total=False):
    messages: Annotated[list[BaseMessage], add_messages]
    reflections_used: int
    idle_nudges_used: int
    steps_in_current_node: int       # 单节点 LLM 回合数

    finalized: bool
    failure_reason: str | None
ToolRunContext (侧通道，每个 task 一份)
@dataclass(slots=True)
class ToolRunContext:
    dag_state: DAGState               # dag / node_status /
                                      # node_outputs / events
    final_answer: AnswerTable | None
    submitted_answers: list[AnswerTable]
    pending_node_done_signals: list[dict]

为什么需要侧通道：LangGraph 的 ToolNode 内部副作用只能通过返回值进入状态。mark_node_done / answer 这类控制流工具要写 DAG 状态、最终答案，单靠 messages 表达不下。

分四类：文件浏览 / 数据探索 / 计算 / 控制流。所有 path 参数都相对 task.context_dir，由 resolve_context_path 兜底防止路径逃逸。

文件 read_json path, max_chars=4000 JSON pretty-print 头部
文件 read_doc ⭐ path, offset, grep, ... 三模式：full(≤32KB) / slice(分页) / grep(正则跳转)
探索 inspect_sqlite_schema path SQLite 表 + CREATE TABLE 原文
探索 inspect_data path, table?, sample_size 列画像（dtype/null/unique/min/max/samples）

计算 query_dataframe path, sql, table_alias CSV/Parquet/JSON → 内存 SQLite + SQL
计算 execute_python code 子进程 + 30s 硬 timeout，cwd=context

Evaluation Framework

三层评测/兜底框架

从 LLM 单次调用到整轮 benchmark，每一层都有独立的失败保护机制。

L1

Fundamental — LLM 调用层

  • • _invoke_with_retry(label=...) 差异化 retry profile
  • • 客户端 Timeout 一律不重试
  • • 429 优先读 Retry-After 头
  • • 指数退避 + full jitter
  • • ChatOpenAI(max_retries=0, timeout=30)
L2

Specialized — Agent 节点层

  • • max_steps_per_node 单节点 step 上限
  • • max_node_attempts 节点软重试
  • • max_replans 计划级重画
  • • max_idle_nudges 空响应救援
  • • max_reflections 答案重提交
L3

Real-World — Benchmark 层

  • • task_timeout_seconds=600 子进程硬切
  • • vote_rounds=3 多候选投票
  • • Retry pass 失败任务再跑一次
  • • vote_all_tasks 末尾签名仲裁
  • • normalize_prediction_csv 落盘前规范化

🎲 多轮签名投票协议

核心算法在 run/vote.py:vote_task_with_candidates。投票按 候选优先级（prediction.csv → r2.csv → r3.csv → ...）解析签名，按规则裁决。

规则 触发条件 胜者 overwrite prediction.csv？
no_candidates 所有候选都无法解析 — 否
single_candidate 只有 1 个可解析 earliest 可解析 仅当胜者非 prediction.csv 才覆盖
two_candidates 恰好 2 个可解析 earliest 可解析（不投票） 同上
majority ⭐ ≥3 候选 + 某签名出现 ≥2 次 第一个等于多数签名的候选 是（atomic replace）
all_different ≥3 候选 + 全部签名互不相同 earliest 候选（=prediction.csv） 否

📐 表签名规范化（投票域）

两份答案签名相等 ⟺ 列签名匹配评分时得到相同结果。compute_table_signature 同时忽略列名/列顺序/行顺序。

def compute_table_signature(columns, rows):
    per_column = []
    for col_index in range(len(columns)):
        cells = [normalize_cell(row[col_index])
                 for row in rows]
        per_column.append(tuple(sorted(cells)))   # 行无序
    return tuple(sorted(per_column))               # 列无序

normalize_cell 7 步优先级

  1. None / "null" / "nan" / "<na>" → ""
  2. bool → "True" / "False"（不当数字）
  3. 数字 → Decimal.quantize(0.01, ROUND_HALF_UP)
  4. 含 T/空格的 ISO datetime → UTC + Z
  5. YYYY-M-D / YYYY/M/D → 零填充 ISO date
  6. 长形式英文 March 1, 2024 → ISO date
  7. strip + 去 \r\n 后保留原文（US/EU 歧义日期不动）

🧮 KDD Cup 评分公式（评分域）

本地 self-eval 在 run/scoring.py，只做最保守的规范化（strip + null literals），不共用投票域规范化，避免本地分数虚高。

Score = max(0,  Recall − λ · (extra / predicted))
λ = 0.5 · 列签名 multiset 匹配 · 列名/列顺序/行顺序均忽略
Recall
matched / gold_columns
extra
predicted_columns − matched
惩罚直觉
1 列 gold + 4 多余列 → 仅得 0.6 分

Case 1 · Dataset Profile 反幻觉前置

📌 任务背景

早期版本 ~80% 的失败是 planner 凭空捏造路径：题目里有 sqlite，模型问 data.db，但实际只有 db/main.sqlite，连环 FileNotFoundError 把 step 预算耗光。

⚠️ 难点

  • • 不能依赖模型记住每道题的目录布局
  • • 不能让 planner prompt 太长（每个 task 都要付出这个成本）
  • • 必须覆盖 sqlite/json/csv/md/txt 五种主要格式

💡 解法

在调用 planner LLM 之前先用 _build_dataset_profile(task) 扫一遍 context/，注入真实文件清单 + sqlite schema + 文件 head 到 prompt，并强制"只引用 profile 里的文件"。

🔧 实现片段

def _build_dataset_profile(task, *, max_depth=4):
    listing = list_context_tree(task, max_depth)
    lines = ["Files under context/ (each line shows the EXACT "
             "path to use as the tool `path` argument):"]

    for entry in listing["entries"]:
        if entry["kind"] == "dir":
            lines.append(f"  [DIR ] {entry['path']}/")
        else:
            lines.append(f"  [FILE] {entry['path']}"
                         f" ({entry['size']} bytes)")

    # Per-format deep dive
    for entry in file_entries:
        suffix = Path(entry["path"]).suffix.lower()
        if suffix in _SQLITE_EXTENSIONS:   # .db / .sqlite
            sections.append(_profile_sqlite(task, path))
        elif suffix in _JSON_EXTENSIONS:    # .json
            sections.append(_profile_json(task, path))
        elif suffix in _CSV_EXTENSIONS:     # .csv
            sections.append(_profile_csv(task, path))
        elif suffix in _DOC_EXTENSIONS:     # .md / .txt
            sections.append(_profile_doc(task, path))
    return "\n".join(lines)

📈 收益

幻觉路径类失败从 ~80% 直接归零；planner prompt 增量约 1-3KB，与 task 总时延比基本不可见。

Case 2 · read_doc 三模式自适应

📌 任务背景

trace 分析（20260506T010810Z）：5/8 step-budget failure 都是 executor 反复 paginate 一个 20-30KB markdown 文档 5-9 次，每次 paginate 都要 LLM 决策一次。task_396 用 8 次 execute_python 反复 grep superhero.md。

💡 解法

同一个工具按入参动态切换三种模式：

mode触发输出
full≤32KB全文 1 次
sliceoffset>0分页 + next_offset
grep传入 grep=<regex>±400字符匹配窗

🔧 三模式调用示例

# 1) full 模式：默认，文档 ≤32KB 一次返回
read_doc(path="doc/Laboratory.md")
# → mode="full", preview=<whole text>, truncated=False

# 2) slice 模式：长文档分页（罕用）
read_doc(path="doc/big.md", offset=8000, max_chars=4000)
# → mode="slice", preview=text[8000:12000],
#   next_offset=12000, truncated=True

# 3) grep 模式（推荐，关键词跳转）
read_doc(path="doc/superhero.md",
         grep="Captain Marvel",
         max_matches=20, context_chars=400)
# → mode="grep",
#   preview="...---..." (匹配窗口用 \\n---\\n 分隔),
#   matches=[{start, end, matched_text}, ...]

📈 收益

  • • 中型文档 (5-30KB) 命中 full，从"5-9 次 paginate"压缩到"1 次"
  • • 关键词查找命中 grep，单次工具调用替代 8 次 execute_python
  • • max_matches=20 + max_chars 双重上限防止贪心 pattern 拉回整文

Case 3 · 多轮投票 + back-fill 文件命名协议

📌 难点：保底 vs 候选

三轮投票要求"轮次产物互不覆盖"（要参与投票），但 entrypoint 后台 5s 一次同步进程要随时能拿到一份保底答案 → 必须有一个稳定的 prediction.csv。

💡 解法

  • • 轮 1 永远写 prediction.csv（保底）
  • • 轮 N≥2 + base 已存在 → rN.csv（候选）
  • • 轮 N≥2 + base 不存在 → prediction.csv（back-fill，前面所有轮都没产出）
  • • 末尾 vote_all_tasks 按签名仲裁，胜者用 atomic replace 覆盖

⚠️ 并发陷阱

必须在 主线程的 submit 循环解析每个 task 的目标文件名，否则 N 个 worker 同时启动时都看到 base 不存在 → 全 back-fill 互相覆盖。

🔧 文件名解析逻辑

def _round_artifact_filename(round_idx: int,
                              base_already_exists: bool) -> str:
    if round_idx <= 1:
        return "prediction.csv"             # 轮 1 总是写保底
    if base_already_exists:
        return f"r{round_idx}.csv"          # 轮 N≥2：候选
    return "prediction.csv"                  # 轮 N≥2：back-fill

🔧 投票裁决（vote.py）

# 候选优先级：("prediction.csv", "r2.csv", "r3.csv", ...)
present = [i for i, s in enumerate(signatures) if s is not None]
if len(present) < 3:
    winner = present[0]                       # earliest 胜
elif max(sig_counts.values()) >= 2:
    winner = first index of majority signature  # 多数票
else:
    winner = present[0]                       # 全异 → earliest

if winner != 0:                               # 胜者非 prediction.csv
    _atomic_overwrite(paths[winner], paths[0])  # tmp + os.replace

Case 4 · Retry Pass · 失败任务"再跑一次"

📌 任务背景

三轮投票后仍有少量 task succeeded=False（典型：被 RateLimit 连杀三次、或全程都没调 answer）。这类 task 已经"白跑"了 3 轮，但只要再试一次，命中概率不低。

💡 解法

  • • 写到独立文件名 prediction_retry.csv + trace_retry.json
  • • 成功 → Path.replace 原子重命名为 prediction.csv / trace.json
  • • 失败 → 删除 retry 文件，原本失败状态保持不变

🌟 不变量

失败的 retry 绝不污染原本的失败状态。只能做加法（成功了提升）不会做减法。

🔧 promote / discard 逻辑

def _promote_retry_artifacts(retry_artifact):
    task_dir = retry_artifact.task_output_dir
    canonical_trace = task_dir / "trace.json"
    canonical_prediction = task_dir / "prediction.csv"

    # Path.replace 在 POSIX 上是原子且会覆盖目标
    (task_dir / "trace_retry.json").replace(canonical_trace)
    if retry_artifact.prediction_csv_path is not None:
        retry_artifact.prediction_csv_path \
            .replace(canonical_prediction)
    return TaskRunArtifacts(...)

def _discard_retry_artifacts(task_output_dir):
    for filename in ("prediction_retry.csv",
                     "trace_retry.json"):
        stale = task_output_dir / filename
        if stale.exists():
            stale.unlink()

Case 5 · entrypoint.sh · 5s 同步守护进程

📌 难点：路径错配

runner 把所有 task 写到 /output/<run_id>/task_<id>/prediction.csv（用 run_id 子目录隔离多轮产物）。但评测系统按规则只读 /output/task_<id>/prediction.csv（顶层路径，没有 run_id）。

💡 解法对比

方案缺点
runner 直接写顶层r2.csv 暴露给评测
跑完后统一拷贝SIGKILL 时所有未拷贝丢失
后台 5s 原子拷贝 ⭐最坏丢 5s 内最后一个

📈 收益

A 榜 7200s 外层 SIGTERM/SIGKILL 时，所有早已写出的答案都已在顶层路径 → 评测系统能立即读到。最坏只丢 5s 窗口内最后一个 task。

🔧 sync_predictions 函数

sync_predictions() {
  shopt -s nullglob
  for src in /output/*/task_*/prediction.csv; do
    task_id="$(basename "$(dirname "${src}")")"
    case "${task_id}" in task_*) ;; *) continue ;; esac
    dst_dir="/output/${task_id}"
    mkdir -p "${dst_dir}"
    # tmp + mv 原子替换，避免读端见到半截文件
    cp "${src}" "${dst_dir}/prediction.csv.tmp"
    mv "${dst_dir}/prediction.csv.tmp" \
       "${dst_dir}/prediction.csv"
  done
}

# 后台进程：每 5 秒扫一次
(while true; do sync_predictions || true; sleep 5; done) &
SYNC_PID=$!

# trap：SIGTERM 时再做一次最后同步（SIGKILL 不可被 trap）
trap 'sync_predictions || true; kill $SYNC_PID 2>/dev/null' \
     EXIT INT TERM
Key Insights & Takeaways

四个维度的设计沉淀

从设计哲学到工程实践，每一条都经过了真实评测的回归压测。

🎯

设计哲学

  • 保底语义优先于最优解
    prediction.csv 永远是"当前最佳"，多轮只能做加法（投票胜者覆盖）不会做减法。任何时刻 SIGKILL 都已有保底答案。
  • 短焦点 > 长全局
    每个 DAG 节点只看 goal + 上游 1-3 句 summary，不看上游工具调用日志。把"几十轮长上下文"压成"几百字符焦点"。
  • 每一层都不信任上一层
    LLM 单次失败 → executor 自我修正 → 节点 attempts → replanner → 多轮投票 → retry pass，5 层兜底层层叠加。
🔬

技术创新

  • DAG-driven 焦点上下文
    planner 显式画依赖图 + scheduler 注入 focused prompt + mark_node_done 跨节点透传 summary，自然支持子任务并行规划。
  • 规范化签名投票
    compute_table_signature 同时忽略列名/列序/行序，normalize_cell 7 步规范化把"近似相同"答案聚合成同一签名，让多数票真正可投。
  • 差异化 LLM 重试
    planner 致命给 2 retries，executor/reflector 失败有外层兜底给 0 retries；客户端 Timeout 一律不重试，429 优先读 Retry-After。
  • 5s 同步守护进程
    把"评测平台只读 /output/task_*/" 与"runner 写 /output/<run_id>/task_*/"两套路径用 cp+mv 原子拷贝衔接。
🌍

实际影响

  • 幻觉路径失败 ~80% → 0%
    Dataset profile 直接消灭这一整类崩溃模式。
  • 中型文档处理 5-9 步 → 1 步
    read_doc full 模式 + grep 模式合计省下大量 step。
  • 单次抽样 → 3 路投票
    A 榜 7200s 预算下 max_workers=2 + vote_rounds=3 仍留 1.4h 缓冲；B 榜 12h 更绰绰有余。
  • SIGKILL 抗损失 5s 上限
    外层 timeout 强杀也只丢窗口内最后一个 task。
🔮

局限与未来

  • vote_rounds 上限 = 3
    超过 3 轮的"全异 → earliest" tiebreak 会引发 incremental vote 路径行为漂移；当前 config 强制校验 1 ≤ vote_rounds ≤ 3。
  • 投票域 vs 评分域规范化分裂
    投票域激进规范化（数字 round 到 2 位、日期归一）让"近似答案"合并；评分域保守，按字节比对避免本地分数虚高。两套规则需要同步维护。
  • 单 task 600s 硬切
    P95 ≈ 356s 时仍有少量长尾 task 撞 timeout。后续可探索"按难度动态超时" 或"提前 mark_node_done 让长尾 task 主动放弃换更多 task 完成"。
  • execute_python 未沙箱化
    受控数据集场景下不必沙箱，但若推广到不可信数据需补完整 sandbox。
Lessons Learned

9 条历史教训（彩蛋）

代码注释里散落的"为什么是这样"，每条都对应一次回归。

#1 为什么从 ReAct 单循环切换到 LangGraph DAG ▼

长上下文模型迷失（step 20+ 后反复读同一文件）、无法表达依赖关系（先读 A 再 join B 全靠隐式记忆）、走错就污染整段对话无法局部回滚。DAG 解法显式拆分 + 节点级 retry。

#2 为什么用子进程而不是线程跑单个 task ▼

线程版本曾遇到单 task 卡 754s（OpenAI SDK 双层 retry 叠加），KeyboardInterrupt 在 C 扩展里失效。改 multiprocessing.Process 后 terminate()+kill() 能强制收尸，子进程崩溃父进程也能从 exitcode 转成 failure_reason 而不让整个 benchmark 挂掉。

#3 为什么 LLM 重试要按调用点差异化 ▼

历史 bug：langchain-openai 内置 max_retries=2 + 自写 max_attempts=5 双层叠加，单次卡顿放大到 540s。修复：ChatOpenAI(max_retries=0, timeout=30) 关掉内置重试，按调用点（planner=2 / executor=0 / reflector=0）差异化分配，客户端 Timeout 一律不重试。

#4 为什么 prediction.csv 是"保底/补位"而不是"轮 1 结果" ▼

最初设计 = 轮 1 结果。问题：轮 1 因 RateLimit 全军覆没时，最终 vote 因 prediction.csv 不存在无法以"earliest"原则裁决。改成"任何阶段只要存在就有保底分"语义后，后续轮次只能做加法不会让结果变更糟。

#5 为什么投票要做"全异 → earliest" ▼

3 个候选签名两两不同时，理论上没信号判断谁对。三种 tiebreak（earliest / 最长 / 最短）权衡后选 earliest：不引入新偏置，简单可解释，且与"prediction.csv 是保底"语义一致。

#6 为什么列签名既忽略列名又忽略列顺序 ▼

KDD Cup 6.2 明确"列签名匹配，忽略列名"，所以 avg / 平均值 / mean 都不影响分数。同时忽略行序：很多 SQL 查询无 ORDER BY 时返回顺序未定义，强制行序匹配会误判正确答案。

#7 为什么数字规范化用 ROUND_HALF_UP 到 2 位（仅在投票域） ▼

投票时不规范化 → 5519.475... 与 5519.48 永远投不出多数。但提交时 prompt 反复强调"不要主动 round"——评分时按字节比 gold，原始精度更安全。两套规则刻意分裂。

#8 为什么文档 ≤32KB 全文返回 ▼

trace 分析（20260506T010810Z）：5/8 step-budget failure 都是 paginate 20-30KB markdown 5-9 次。SHORT_DOC_FULL_RETURN_THRESHOLD = 32_000 把这一类 step 浪费降到 1 次；32KB 上限避免巨型病历炸 LLM 上下文。

#9 为什么 task_timeout 收紧到 600s 而不是 1800s ▼

原 1800s 让 4 worker 同时卡死时吃光大半总预算（A 榜 7200s）。本地 P95≈356s + 20% 缓冲 → 360s，让长尾 task 主动放弃换更多其他 task 完成。提交配置最终选 600s + workers=2 + vote_rounds=3，整体在 7200s 内仍有 1.4h 缓冲。
