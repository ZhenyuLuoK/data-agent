# boost-agent 架构总览

> 本文从架构层面总结 `boost-agent`（KDD Cup 2026 DataAgent-Bench 参赛方案）的整体设计，省略代码与参数细节，重点阐述每一层的**设计动机**与**架构优点**。

---

## 一、整体定位

### 1.1 业务场景

`boost-agent` 是一个面向"自然语言数据分析问题 + 文件型上下文（CSV / JSON / SQLite / Markdown）"的 Agent 系统。给定一道题目（一段自然语言问题 + 一个上下文目录），Agent 必须仅通过提供的工具读取这些文件、推理并产出一张最简表格作为答案。

### 1.2 评测规则与硬约束

整套架构的所有取舍都围绕以下四条评测平台的硬约束展开，理解架构必须先理解这四条：

- **打分规则**：评测器按列签名做集合匹配（**忽略列名、列顺序**），并对**多余列**施加线性惩罚。最终得分 = 召回率 − 系数 × 多余列比例，**得分以 0 为下限**。这意味着"多答列"会被惩罚，"漏答列"会拉低召回，"列名写得对不对"则完全无关。
- **运行时预算**：评测平台用外层 `timeout` 套住整个容器进程，到时先 SIGTERM 后 SIGKILL，进程随时可能被强行收尾。
- **目录契约**：评测平台只挂载固定的输入 / 输出路径，且只读输出路径下一个**特定文件名**的答案文件。
- **运行期不可联网**：除调用模型 API 外，镜像内不允许任何对外网络访问，否则按违规处理。

### 1.3 一句话概括

> **以 LangGraph DAG 为推理骨架，以多轮投票 + 失败重试为稳定性手段，以"保底文件"为评测对接契约的数据分析 Agent。**

### 1.4 高层设计原则

下文的所有架构组件都是为了实现以下五条原则之一而存在，建议在阅读后续章节时持续对照：

1. **DAG 驱动**：用结构化的子任务图替代单一的长对话循环，避免长上下文中迷失。
2. **失败兜底层层叠加**：节点内步数预算 → 节点级重试 → 计划级 Replan → 反思器 RETRY → 多轮投票 → 单题救援；每一层都有有限上限。
3. **保底输出语义**：保底答案文件一旦写出就立刻被同步到评测目录，后续轮次只能用原子覆盖在保底之上做加法。
4. **强反幻觉**：规划阶段把真实的目录清单 / Schema / 文档样本注入给模型，杜绝凭空捏造路径。
5. **签名规范化**：投票与本地评分都基于"列签名"做集合匹配，自动忽略列序、行序、数字精度、日期格式差异。

### 1.5 技术栈选型（架构级）

| 维度 | 选型范式 | 架构含义 |
| --- | --- | --- |
| Agent 编排 | **LangGraph 状态图（StateGraph）** | 用有向图 + 条件路由替代单循环，把"下一步做什么"显式化 |
| LLM 客户端 | **OpenAI 兼容协议** | 不绑定单一厂商，可在 OpenAI / Qwen 等后端之间切换 |
| 命令分发 | **CLI 命令分组** | 状态查看、单题调试、整集运行、本地评分四类操作解耦 |
| 数据处理 | **DataFrame + 内存 SQL** | 计算类工具内部统一以 SQL 为查询语言 |
| 配置 | **不可变结构化配置 + 环境变量展开** | API Key 不落镜像、本地与提交配置文件解耦 |

## 二、分层架构

系统自顶向下被划分为相互解耦的六层，每一层只负责一个明确的职责：

```
┌────────────────────────────────────────────────────────────┐
│  评测平台 / Docker 接入层（entrypoint）                      │
│   ─ 同步保底答案到评测目录、屏蔽多轮中间产物                  │
├────────────────────────────────────────────────────────────┤
│  CLI / 配置层                                               │
│   ─ 命令入口、配置解析（环境变量展开）、运行控制              │
├────────────────────────────────────────────────────────────┤
│  数据集层                                                   │
│   ─ 题目目录索引、上下文路径不变量、不可变 Schema           │
├────────────────────────────────────────────────────────────┤
│  运行调度层（Runner / Vote / Retry / Score）                 │
│   ─ 多轮调度、隔离执行、投票合并、失败救援、本地评分          │
├────────────────────────────────────────────────────────────┤
│  Agent 核心层（LangGraph DAG）                              │
│   ─ 规划、调度、执行、反思、兜底、可视化的节点化协作          │
├────────────────────────────────────────────────────────────┤
│  工具层                                                     │
│   ─ 文件预览 / 数据探索 / 计算执行 / 控制流，统一受路径沙箱   │
└────────────────────────────────────────────────────────────┘
```

层与层之间通过**明确的契约**解耦：目录结构、文件名约定、不可变状态字段、强校验的工具签名。任意一层都可以独立替换或调整而不影响其他层。

下面逐层阐述。

## 三、Agent 核心层：LangGraph DAG

这是整个系统最核心、也是最具特色的设计。它把传统的"ReAct 单循环"重构成了一个**多节点协作的状态机**。

### 3.1 节点拓扑

整个推理过程被实现成 9 个节点的有向图。按职责分组：

**主流程节点**

- **Planner（规划器）**：题目入口，仅在首次进入时运行一次，产出结构化的子任务 DAG。
- **Scheduler（调度器）**：每次被路由到时挑选下一个 ready（依赖已就绪）的子任务节点，并为执行器构造"聚焦提示"。
- **Executor（执行器）**：在当前聚焦的子任务节点内调用 LLM，决定下一步是调工具、写文本还是结束当前节点。
- **Tools（工具节点）**：实际执行执行器发出的工具调用。

**校验与终止节点**

- **Reflector（反思器）**：在执行器提交最终答案后被路由到。对答案做合规性校验，OK 则结束，否则要求重交。
- **Finalize**：终止节点，触发整张图的退出。

**兜底节点**

- **Replanner（重规划器）**：原 DAG 无法继续推进时被触发，吃前一版计划与失败原因，重新出 DAG。
- **NodeFailure（节点级兜底）**：单节点的步数预算耗尽时被路由到，决定是软重试当前节点还是把它标记失败、上抛给重规划器。
- **Nudge（轻量唤醒）**：执行器返回空响应时被路由到，以极低代价（注入一条简短提示）让 LLM 重新发声。

### 3.2 路由关系（节点之间如何流转）

节点拓扑只是"有哪些节点"，真正决定 Agent 行为的是**条件路由**——执行器的每次返回值都会经过路由函数判定下一站去哪：

```
                                 ┌──────────────────────────────┐
                                 ▼                              │
   START → Planner → Scheduler → Executor → Tools ──────────────┤
              ▲          │          │ ▲                         │
              │          │          │ └── Nudge ◀────(空响应)───┤
              │          │          │                           │
              │          │          └── (提交 answer) → Reflector
              │          │                                  │
              │          │                                  ├─ OK    → Finalize → END
              │          │                                  └─ RETRY → Scheduler
              │          │
              │          └── 无 ready 节点 / 节点失败 → NodeFailure → Scheduler
              │                                              │
              │                                              ▼
              │                                        （重试预算耗尽？）
              │                                              │
              │                                              ▼
              └─────────────────────── Replanner ────────────┘
                          （Replan 预算耗尽 → Finalize → END）
```

要点：

- **Tools 节点只是"执行工具"**，路由由"调用了哪个控制流工具"决定：调了"提交答案" → Reflector；调了"标记节点完成" → Scheduler；调了普通数据工具 → Executor。
- **Reflector 的 RETRY 不是回到 Executor**，而是回到 Scheduler 重新聚焦终节点；这样可以复用"清空当前节点状态再进入"的统一入口，避免 RETRY 路径出现状态不一致的特殊情况。
- **NodeFailure 与 Replanner 是两层兜底**：单节点失败先尝试同节点软重试，达到上限才上抛触发计划级重规划。

### 3.3 共享状态：双通道架构

LangGraph 原生提供一条状态通道——`messages` 列表，由 reducer 自动追加。但是它有一个先天限制：**ToolNode 内部产生的副作用只能通过返回值进入消息流**。这对"标记节点完成"、"提交最终答案"这类**控制流动作**是不够的——它们要写的是 DAG 的节点状态、最终答案对象，根本不属于"消息"语义。

为此，架构层面引入了第二条通道——**ToolRunContext 侧通道**：

```
┌─────────────────────────────────────────────────────────────┐
│                    LangGraph StateGraph                      │
│  ┌────────────────────┐         ┌───────────────────────┐   │
│  │  messages 主通道   │         │  ToolRunContext 侧通道 │   │
│  │  （LLM 对话流）   │         │  （DAG 状态 / 控制流） │   │
│  │                    │         │                        │   │
│  │  - HumanMessage   │         │  - dag 拓扑 / 状态    │   │
│  │  - AIMessage       │         │  - 节点输出摘要       │   │
│  │  - ToolMessage     │         │  - 最终答案对象       │   │
│  │                    │         │  - 历史所有提交答案   │   │
│  └────────────────────┘         └───────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
        ▲                                    ▲
        │                                    │
   每次 LLM 调用读写                  控制流工具直接读写
```

- **per-task 隔离**：每道题在运行开始时新建一个独立的 ToolRunContext，工具实例和图节点都绑定到同一个 context 引用。任意两道题之间的状态完全隔离，杜绝跨题串扰。
- **强校验入口**：控制流工具对入参做严格校验（节点 ID 是否存在、是否是当前聚焦节点、output 是否非空等），任何不合法尝试都会被立刻打回成工具错误消息，模型下一拍就能修正。
- **scheduler 在下一拍即可感知**：工具直接写 `dag.node_status[...]` 后，scheduler 下一次运行就能看到，无需额外的事件总线。

### 3.4 子机制 1：Dataset Profile —— 反幻觉的核心

实测中最大的失败模式是模型**凭空捏造文件路径**（题目说有 sqlite，但模型直接去读 `data.db`，而真实文件可能叫 `db/main.sqlite`）。

为此，规划阶段在调用 LLM 之前，先扫描该题的整个上下文目录，构造一份 **Dataset Profile** 注入到 Planner 的 system prompt 中：

- 真实存在的目录与文件清单（含路径与大小）；
- 每个 SQLite 文件的全部表结构；
- 每个文档 / CSV / JSON 的头部样本。

并在 prompt 中**强制要求**："只允许引用 profile 中出现的文件"。这把"反幻觉"从一个"靠提示词反复约束"的脆弱机制变成了"模型根本看不到不存在的路径"的结构性保证。

### 3.5 子机制 2：Focused Prompt —— 长上下文压缩

DAG 各节点之间不直接共享对话历史。每次 Scheduler 选中一个节点时，构造的"聚焦提示"**只包含**：

- 当前节点的 goal 和期望输出；
- 它所依赖的上游节点的**事实摘要**（由那些节点完成时通过控制流工具上报的简短文本）。

上游节点的工具调用日志、消息历史**不会**进入下游节点的 LLM 输入。这把"长上下文 ReAct"变成了"短上下文焦点接力"，让一道题的总 token 消耗保持在可控范围，也让模型在每个节点都"轻装上阵"。

### 3.6 子机制 3：执行器三层自我保护

执行器位于 LLM 自由度最高的位置——它可以选择调任意工具、写任意文本。为防止 LLM 的常见失败模式吃光预算，执行器外面包了三层观测器：

- **重复调用检测**：连续几轮用完全相同参数调同一工具时，注入强提示让模型立刻提交当前结果或更换工具/参数。
- **长文档过用检测**：连续多次调用文档读取工具（哪怕参数不同）时，建议改用列目录或受限 Python 或直接结束当前节点。
- **步数预算软警告**：节点内步数接近上限时，注入"立刻提交当前结果，哪怕是部分答案"的提示。
- **空响应不计步**：LLM 偶发返回空内容时不计入步数预算，由 Nudge 节点低成本恢复，避免几次空响应就把节点预算耗光。

这一层是"LLM 自由度"与"硬约束"之间的中间层防护，把模型的常见反模式拦截在它造成实质损失前。

### 3.7 子机制 4：差异化 LLM 重试策略

整个 Agent 中所有 LLM 调用走同一个统一入口，但按调用点采用**不同的重试 profile**：

| 调用点 | 重试策略 | 设计依据 |
| --- | --- | --- |
| Planner | 多次重试 + 指数退避 | 失败将导致整个 task 死，必须给重试机会 |
| Executor | 不重试 | 失败有节点级 / 计划级 / 投票级多层外层兜底，重试无意义 |
| Reflector | 不重试 | 反思失败不影响保底答案（已写出），损失可承受 |
| 任意调用遇到 429 | 优先读 Retry-After 头 + 长退避上限 | 速率限制有标准协议，遵守即可 |
| 任意调用客户端超时 | 一律不重试 | 客户端超时多半源于模型本身慢，重试只会再超时 |

底层 SDK 内置的重试被显式关闭，避免与本层重试形成"双层叠加"导致单次卡顿被放大数倍。

### 3.8 子机制 5：Reflector 的四维语义校验

Reflector 不是简单的"答案存在性检查"，而是直接对应**评分公式**的四个惩罚维度：

| 校验维度 | 对应风险 |
| --- | --- |
| **结构**：列名 / 列数 / 行数与问题语义匹配 | 列数不对 → 召回率直接拉低 |
| **冗余列**：是否多答了无关列 | 直接触发 `λ × extra/predicted` 惩罚项 |
| **聚合检查**：问"how many"却返回多行 | 显然没做 COUNT/SUM，召回率为 0 |
| **格式**：日期 / null / 大小写 / 数字精度 | 与评测器期望格式不一致会导致签名不匹配 |

Reflector 的存在让"评分公式"从"线上一次性的黑盒"变成了"线下可前置的检查项"，把多余列、漏聚合等高频错误在落盘前就拦下来。

### 3.9 架构优点

- **强反幻觉**：通过 Dataset Profile 把反幻觉从"提示词约束"升级为"结构性保证"。
- **可视化与可调试**：DAG 拓扑与节点状态被增量渲染成图落盘，事后 trace + 图能精确还原"哪一步走错了"。
- **失败兜底层层叠加**：节点内步数 → 节点级重试 → 计划级 Replan → 反思 RETRY → 多轮投票 → 单题救援，形成漏斗式收敛。
- **自我保护机制前置**：执行器的三层保护把"模型常见反模式"拦在造成实质损失前。
- **per-task 状态隔离**：每题独立的 ToolRunContext 让多题并行成为可能而无串扰。

## 四、工具层

### 4.1 工具的四类角色

工具被划分为四类清晰的角色，每一类职责互斥、能力互补：

| 类别 | 代表能力 | 角色定位 |
| --- | --- | --- |
| **文件类** | 列目录、glob 匹配、CSV/JSON/文档预览 | 探索上下文、定位输入 |
| **探索类** | SQLite Schema、列画像（dtype/null/unique/min/max/样例） | 在不下载全量数据的前提下了解数据形状 |
| **计算类** | 上下文 SQL（直接查 SQLite）、DataFrame SQL（CSV/JSON/Parquet 转内存表）、受限 Python | 真正执行数据加工与聚合 |
| **控制流类** | 标记节点完成、提交最终答案 | 驱动 DAG 状态流转，不读不写文件 |

### 4.2 设计动机

**(1) 以"压缩 step 数"为第一目标**

每一次 LLM 调用都消耗预算与时间。工具被刻意设计成"高信息密度"——一次调用顶 ReAct 风格 2-3 次原子调用：

- 列画像工具一次返回 dtype / null / unique / min / max / 样例，替代"读 CSV → df.head() → df.dtypes → df.shape"三连击；
- 文档读取工具内置三种模式（全文 / 分页切片 / 正则匹配），让模型能一次跳到关心的段落而不是反复翻页；
- DataFrame SQL 把"读 CSV → pandas group_by → to_dict"这种典型工作流压缩成一次工具调用，并用 SQL 错误信息替代 Python KeyError，让错误更可解释。

**(2) 路径沙箱的双层防御**

所有工具的 `path` 参数都相对于该题的上下文目录解析，统一走一个路径解析函数，提供两层防御：

- **路径逃逸阻断**：通过 `..` 或符号链接试图跳出上下文目录的访问被直接拒绝；
- **缺失文件友好提示**：路径不存在时，错误消息会附带真实目录列表与"建议先列目录"的提示，让模型下一拍就能自我修正，省一次重规划。

**(3) 错误消息当作"修正信号"**

工具异常的类型与原文被直接转成工具消息回传给模型，富错误信息（"文件不存在；当前目录下有这些条目"）能直接驱动模型自我修正，而不需要再消耗一轮 LLM 调用去问"应该读哪个文件"。

**(4) 强 schema 输入**

所有工具用结构化 schema 声明参数，LLM 拿到的是显式字段定义而不是自由文本，从源头降低参数错传概率。

**(5) 控制流工具的强校验**

"标记节点完成"和"提交最终答案"对入参做严格校验：DAG 必须存在、节点 ID 必须有效、必须是当前聚焦节点、答案表格的列数与行长必须自洽等。任一不满足立刻返回工具错误，避免"看似成功实则状态错乱"。

**(6) 受限 Python 的硬边界**

最后兜底的受限 Python 工具有明确的硬边界：硬性时间上限、工作目录强锁在题目上下文目录下、stdout 捕获作为输出。它不是为了沙箱安全（数据集本身受控），而是为了**预算可控**——预算耗尽时不能让模型放大超时，而应改用 SQL 工具或分块处理。

### 4.3 备份引擎：Legacy ReAct 路径

工具层同时保留了一套**老式 ReAct 工具注册表**作为备份引擎：当主路径（LangGraph DAG）出现致命问题时，调度层可以显式注入 model + tools，切回单循环 ReAct 模式跑同一道题。这是"双引擎"架构选择——主引擎追求最优能力，备份引擎追求最低假设、最简实现，**能跑出答案就比卡住强**。

### 4.4 架构优点

- **工具集小而锐利**：只保留少数几个高密度工具，模型选择空间小，不容易陷入"该用哪个"的犹豫。
- **每一类都有兜底**：上下文 SQL → DataFrame SQL → 受限 Python，不同维度上互相补位；任何一类临时失效都还有路径继续推进。
- **错误信息驱动修正**：把"工具失败"从"扣预算的事故"变成"驱动模型自修正的信号"。
- **控制流与数据流严格隔离**：控制流工具不读写文件、强校验、状态显式；数据流工具不改 DAG 状态。两类工具语义互不重叠。

## 五、运行调度层：多轮投票 + 失败重试

Agent 单次输出存在天然随机性，调度层的使命是**把这种随机性压成可投票的多份候选，再用规范化签名做多数决**。

### 5.1 隔离执行：每题一进程

每道题以独立子进程运行，受硬性时间预算保护。这一选择的关键动机是：

- LangGraph + LLM SDK 的调用栈在某些异常路径下会陷入纯 C 扩展（如 SSL 握手），常规 Python 异常（包括 KeyboardInterrupt）在 C 扩展里未必生效，线程根本无法被中断；
- 子进程可以先发 SIGTERM 软杀，宽限期后发 SIGKILL 硬杀，无论卡在哪一层都能强制收尸；
- 子进程崩溃（OOM、段错误）能被父进程通过退出码捕获并转成可记录的失败原因，不会让整个 benchmark 跟着挂掉。

调度层还提供**两条执行路径**：

- **默认路径**：用子进程隔离 + 硬超时跑 LangGraph DAG，适合多题并发的正式运行；
- **进程内路径**：当显式注入 model + tools 时直接在当前进程跑（适合 Legacy ReAct / 单线程调试 / 单元测试）。检测到这种情况时强制把并发 worker 数压到 1，避免共享 LLM 客户端实例的线程不安全问题。

### 5.2 多轮调度与"保底文件"契约

每道题独立跑多轮，每一轮都尝试给出一份候选答案。文件命名规则严格遵循以下契约：

| 阶段 | 该轮该题的输出文件名 |
| --- | --- |
| 第 1 轮 | 永远是"保底文件" |
| 第 N 轮（N≥2），保底文件已存在 | 候选文件（按轮序编号） |
| 第 N 轮（N≥2），保底文件仍不存在 | **补位**写入保底文件 |

**关键不变量**：保底文件代表"当前最佳"的语义。容器外的同步守护进程只看保底文件——只要它存在就有保底分。后续轮的候选文件只参与投票，不会被评测系统看到；最终投票胜者会用原子覆盖把保底文件升级为更优答案。

**并发安全的微妙之处**：候选文件名规则必须在**主线程提交任务时**就预先确定。否则同一轮的多个 worker 同时启动时都会看到"保底文件不存在"，全都判定要补位，互相覆盖。在主线程提交时确定每个题的目标文件名就根除了这个竞态。

### 5.3 投票域的签名规范化

候选答案被规范化成"列签名集合"做多数决：

- 每一列的所有单元格被规范化后排序成元组（**行无序**）；
- 所有列再排序成元组（**列无序，列名也不参与**）；
- 两份答案签名相等当且仅当它们用列签名匹配方式打分时会得到相同结果。

单元格规范化按优先级处理多种数据形态：null 字面量统一为空、布尔值不冒充数字、数字按固定精度四舍五入、ISO 与零填充日期 / 长形式英文日期统一格式、其余文本仅做空白裁剪。**有歧义的日期格式**（如 US 与 EU 风格的斜杠日期）一律不动，避免静默换月日。

### 5.4 投票裁决规则

| 候选数量 | 裁决规则 |
| --- | --- |
| 0 个有效候选 | 无候选可裁，保留原状（多半是该题彻底失败） |
| 1-2 个候选 | 取最早一轮（轮 1 通常最稳定，无并发干扰） |
| 3+ 个候选，存在多数签名 | 取该多数签名出现的最早轮次 |
| 3+ 个候选，全异 | 取最早一轮 |

裁决落地通过**原子覆盖**完成：先写临时文件再 rename，保证容器外的同步进程读到的要么是旧内容、要么是新内容，绝不会读到半截。

为什么 1-2 候选不投票：投票的本意是"多数压少数"，候选不足时缺乏信号，按"最早一轮"是简单稳妥的策略，与"保底文件"语义天然一致。

### 5.5 双归一化：投票域 vs 评测域分离

签名规范化在系统中**有两套独立实现**，分别服务于不同目的：

| 维度 | 投票域 | 评测域（本地 self-eval） |
| --- | --- | --- |
| 强度 | 激进（数字精度统一、日期格式统一、长文本归一） | 保守（仅 strip + 少数 null 字面量） |
| 目的 | 最大化候选合并能力 | 贴合真实评测器行为 |

两者**不混用**、**不共享代码**。这是有意的架构隔离：投票时激进归一化让"看似不同实则同义"的答案合并以提高聚合能力；评测时保守归一化让本地分数尽量贴近线上真实分，避免本地虚高。

### 5.6 落盘前的最终规范化

投票胜者覆盖保底文件后，调度层还会对最终保底文件做一次规范化重写——把每个单元格走一遍投票域的归一化函数后写回。这是"评测系统看到的字节"层最后的格式统一，让模型输出的奇形怪状的数字、日期、null 都被规整成评分器期望的形式。

### 5.7 失败重试 Pass

所有投票轮跑完后，对仍失败的题目再单独跑一次：

- 写到独立的临时文件名，避免污染原本的失败状态；
- **成功**：用原子重命名把临时产物提升为正式答案，trace 同样升级；
- **失败**：删除临时产物，原本的失败状态保持不变，**不会让重试反而把状态搞乱**。

这一设计的关键：**重试发生在投票之后**。投票本身已经能挽救一部分波动型失败，剩下仍失败的多半是稳定型失败，对它们再单独投入一次预算更划算。

### 5.8 可观测性维度

调度层把每一轮、每一次投票、每一次重试的事件都落盘成结构化产物：

- 每题每轮的完整 trace（含每一步的思考、动作、观测）；
- 每题的投票摘要（每个候选的状态、签名、最终采用的裁决规则）；
- 全 run 总结（轮次统计、重试统计、投票统计）；
- 本地评分报告（每题召回率、多余列数、最终分）。

特别值得一提的是投票摘要中的**候选状态字段**（ok / missing / empty / unparseable）——这是**纯可观测性字段，不参与投票裁决**，纯粹用于事后定位"为什么某轮全军覆没"。这是有意的架构隔离：可观测性面与控制流面互不干扰。

### 5.9 本地 Self-Eval：评分层

调度层还包含一个独立的"本地 self-eval"组件，按照评测平台的评分规则对每题打分（召回率减去多余列惩罚），落出每题分数与汇总统计。它与投票域的归一化函数刻意分离——评测域必须保守，让本地分尽可能贴近线上真实分。这一组件是"线下回归测试"的基石，让任何代码改动都能立刻量化对得分的影响。

### 5.10 架构优点

- **预算可控**：所有失败兜底都是有限轮数 / 有限重试，不存在"无限循环烧预算"的可能。
- **稳定性显著优于单跑**：多轮投票把模型的偶发性错误（一次答错列、一次漏 GROUP BY）有效过滤，只要正确答案是多数，就能恢复。
- **保底语义全程在线**：任何阶段崩溃都至少留下保底答案；后续轮只能在保底之上做加法，绝不会让结果变更糟。
- **观测/控制分离**：候选状态等观测字段不参与裁决，避免"日志变成隐式控制流"的反模式。
- **本地与线上对齐**：本地 self-eval 使用与线上一致的保守归一化，避免本地虚高。

## 六、CLI / 配置层

### 6.1 关键机制

- **命令分发统一入口**：状态查看、单题元数据查看、单题运行、整集运行、本地评分都通过同一个命令入口分发到不同子命令。
- **配置环境变量展开**：模型名、API 地址、API Key 等敏感字段通过环境变量注入，配置文件中以占位符形式声明（支持默认值），**不允许 API Key 硬编码进镜像或源码**。
- **不可变配置对象**：配置加载后被冻结成不可变对象向下传递，跨层不会被意外修改，且天然线程/进程安全。
- **路径解析约定**：YAML 中的相对路径以项目根为基准解析为绝对路径，绝对路径直接保留。这样同一份配置在任何 cwd 下运行都指向同一处，而提交场景的绝对挂载路径不会被错误前缀。
- **三套配置分场景**：示例配置、本地开发配置、提交镜像配置三者解耦，每一份对应一个明确的使用场景（占位符示例 / 真实开发 key / 镜像内占位符 + 绝对路径）。
- **懒加载策略**：仅在真正运行 benchmark 的命令中才加载重型依赖（LangGraph、绘图库等），让"查看状态 / 打分"这类轻命令保持快速启动。
- **配置项校验前置**：投票轮数等关键配置在加载阶段就做边界校验，配置错误立刻报错而不是运行到一半才崩。

### 6.2 设计动机与优点

- **符合评测平台合规要求**：API Key 不落镜像、运行期不联网（除模型 API 外）是参赛硬性约束；环境变量展开机制让源码与密钥彻底解耦。
- **本地与提交无缝切换**：同一份代码通过切换配置就能在"本地小数据集快速冒烟"与"提交镜像全量评测"之间切换，无需修改源码。
- **快慢命令分离**：开发者高频使用的轻命令几乎瞬时启动，不会因加载 Agent 链路而被拖慢，显著提高调试效率。
- **快速失败优于安静崩溃**：配置不合法立刻报错；任何字段名漂移立刻可见。

## 七、数据集层

### 7.1 关键机制

- **目录契约固定**：每道题一个目录，含元数据 JSON 和上下文子目录；所有工具看到的"路径"都是上下文目录下的相对路径。
- **不可变 Schema**：题目记录、上下文资产、最终答案表格都被定义为不可变数据结构，跨层传递时不会被意外修改。
- **快速失败**：元数据字段名漂移会立刻报错，不允许"安静地用错误数据继续跑"。
- **稳定排序**：题目按编号的整数大小（而非字典序）排序，确保任意两次运行看到的题序一致，便于跨 run 对比 trace。
- **筛选能力**：支持按题号白名单、难度、难度集合做筛选，便于在调试时只跑特定子集。

### 7.2 设计动机与优点

- **路径不变量是整个工具沙箱的基石**：所有工具都假设路径相对于上下文目录解析；这个不变量一旦被打破，沙箱就形同虚设。把"上下文路径"集中在一处定义，让沙箱只有一个被信任的入口。
- **不可变结构便于并发**：题目对象在多线程 / 多进程之间共享时不会出现竞态。
- **稳定排序便于回归**：排序与筛选稳定，让"昨天跑成功今天跑失败"的对比能精确定位到具体题号。

## 八、Docker / Entrypoint 接入层

### 8.1 关键机制

- **后台同步守护**：评测平台只读特定固定路径下的答案文件，但 Runner 把多轮产物写在带运行 ID 的隔离目录中。后台进程定期扫描所有运行目录下的保底文件，**原子拷贝**到评测路径。
- **信号收尾 trap**：在收到平台终止信号时，做最后一次同步再退出；即使被强杀，由于轮询频率远低于平台杀进程的宽限期，损失也被压在很小的窗口内。
- **运行期清空依赖镜像源**：构建期通过镜像源加速依赖安装；安装完成后清空相关环境变量，避免运行期任何隐式联网行为被判违规。
- **环境变量自检不泄漏**：启动时打印关键环境变量是否已设置，但**只打印 set / unset**，绝不打印 Key 本身，避免泄漏到评测日志。
- **不预创建运行目录**：每次启动由 Runner 自己生成时间戳目录，避免重复评测撞目录覆盖产物。

### 8.2 设计动机：三个矛盾需求的统一解

接入层要解决三个看似矛盾的需求：

1. **多轮投票需要把候选文件互相隔离**——不能让评测看到中间候选；
2. **评测平台只看一个固定路径**——不知道运行 ID；
3. **进程随时可能被强杀**——不能依赖"跑完后统一拷贝"。

可选方案对比：

| 方案 | 缺点 |
| --- | --- |
| Runner 直接写评测路径 | 多轮投票时候选文件都暴露给评测，违反"只读保底文件"语义；中间状态被评测看到 |
| 跑完后再统一拷贝 | 一旦被强杀，所有未拷贝答案丢失 |
| **后台同步 + 隔离目录（采用）** | 唯一能同时满足三个需求的方案 |

第三方案的具体落地：Runner 仍写到带运行 ID 的子目录隔离多轮产物，**后台进程按固定周期原子拷贝保底文件**到评测目录。这样：

- 第 1 轮一旦写出保底文件，几秒内就同步到评测路径，就算后续被强杀也已经有保底答案；
- 多轮投票胜者覆盖隔离目录的保底文件后，下一个同步周期把胜者拍上去；
- 候选文件永远不会出现在评测目录，符合"只读保底文件"。

### 8.3 架构优点

- **评测对接零侵入**：Runner 不需要知道"评测看哪个路径"，它只管按自己的语义写文件；评测对接完全在 entrypoint 层完成。Runner 与评测平台契约彻底解耦。
- **强壮性极高**：无论平台何时发信号、发什么信号，都有合规答案保底。能 trap 的信号做最后一次同步把损失降到 0；不能 trap 的信号也只丢失最近一个同步周期的进展。
- **合规审计友好**：日志里不出现 Key、运行期无隐式联网、构建期与运行期网络配置严格分离。

## 九、端到端时序

把所有层串起来看，一次完整评测的时序是：

```
评测平台 docker run
    │
    ▼
entrypoint
    ├─ 校验环境变量、检查输入目录
    ├─ 启动后台同步守护（周期性把保底文件原子拷贝到评测路径）
    └─ 启动 dabench
              │
              ▼
        加载配置（环境变量展开） → 索引数据集 → 创建运行目录（带时间戳）
              │
              ▼
        ┌── 第 1 轮：并行跑所有题，落保底文件 ──────────────────┐
        │                                                      │
        │   ┌── 子进程隔离 + 硬超时 ──────────────────────┐    │
        │   │  LangGraphAgent.run(task):                  │    │
        │   │   Planner（注入 Dataset Profile）→ DAG      │    │
        │   │   ├─ Scheduler（注入 Focused Prompt）       │    │
        │   │   ├─ Executor + Tools（数据/控制流分离）    │    │
        │   │   ├─ mark_node_done → Scheduler（下一节点） │    │
        │   │   ├─ ... 各子任务节点接力                    │    │
        │   │   ├─ 终节点提交 answer → Reflector          │    │
        │   │   │   ├─ OK    → Finalize → END             │    │
        │   │   │   └─ RETRY → Scheduler 重新聚焦终节点   │    │
        │   │   └─ 节点失败 → NodeFailure → Replanner     │    │
        │   └─────────────────────────────────────────────┘    │
        │                                                      │
        │   落 trace.json + prediction.csv（保底文件）         │
        │                                                      │
        │   ╔═════════════════════════════════════════════╗    │
        │   ║ 后台同步进程把保底文件拍到评测路径          ║    │
        │   ║ → 即使后续被强杀也有合规答案               ║    │
        │   ╚═════════════════════════════════════════════╝    │
        └──────────────────────────────────────────────────────┘
              │
              ├─ 第 2、3 轮：候选文件隔离写出（保底文件不动）
              │   或在保底文件不存在时补位写入保底文件
              │
              ├─ Retry Pass：失败题最后一搏（写到独立临时文件，
              │   成功则原子重命名提升为保底，失败则丢弃）
              │
              └─ 全表投票：签名规范化 → 多数决 / earliest →
                 胜者原子覆盖保底文件 → 落最终规范化 → 落总结
              │
              ▼
        dabench 退出 → entrypoint trap：最后一次同步 → 容器退出
              │
              ▼
        评测平台读评测路径下的保底文件 → 按列签名打分
```

每一层只做自己的事，层与层之间通过明确的契约（目录结构、文件名约定、不可变状态字段、强校验工具签名）解耦，可以独立替换或调整。

## 十、设计哲学总结

把分散在各层的设计取舍归纳为五条核心原则：

### 10.1 DAG 驱动，反长上下文

把"长对话"切成"短焦点"，每个节点只看自己需要的事实，从根上避免模型迷失。Dataset Profile 让规划只能引用真实路径；Focused Prompt 让节点之间只透传事实摘要而不传对话历史；执行器三层自我保护把模型常见反模式拦截在它造成实质损失前。

### 10.2 保底语义优先于最优语义

宁可先落一份合规答案再优化，绝不接受"算到最好但没落盘"。多轮、投票、重试都建立在保底之上做加法。任何阶段崩溃，都至少留下保底答案；后续轮的胜者通过原子覆盖升级保底，绝不会让结果变更糟。

### 10.3 失败的爆炸半径要可控

工具失败 → 节点重试 → 计划 Replan → 反思 RETRY → 多轮投票 → 单题救援，每一层都有有限上限，避免无限烧预算。LLM 重试还按调用点差异化——致命调用给重试机会，有外层兜底的调用不重试，避免重试栈层层叠加。

### 10.4 控制流必须显式且强校验

节点完成、答案提交都做成专门的工具与状态字段，不依赖 LLM 自由文本。控制流走 ToolRunContext 侧通道，与 messages 主通道严格分离。任何不合规尝试立刻打回成工具错误，模型下一拍就能修正而不会让状态默默错乱。

### 10.5 投票域与评测域不混用

归一化在不同目的下用不同强度——投票域激进合并、评测域保守贴合，**两套独立实现互不共享代码**，避免"本地高分线上崩"。可观测性字段（如候选状态）也与控制流字段严格分离，避免日志变成隐式控制流。

## 十一、可观测性面：架构的"第二维度"

除了功能维度的六层分层，系统还有一个独立维度——**可观测性面**，由各层在运行中持续落盘的结构化产物组成：

| 产物类别 | 产生层 | 用途 |
| --- | --- | --- |
| 每题每轮的完整 trace（思考 / 动作 / 观测 / 是否成功） | Agent 核心层 | 事后还原"为什么这道题答错了" |
| DAG 拓扑与节点状态图（增量重绘） | Agent 核心层 | 直观看到 DAG 在哪一步卡住 |
| 每题的投票摘要（候选状态 / 签名 / 应用规则） | 调度层 | 定位"为什么某轮全军覆没" |
| 全 run 总结（轮次统计 / 重试统计 / 投票统计 / 各题最终状态） | 调度层 | 给整次运行一份高层报告 |
| 本地评分报告（每题召回率 / 多余列数 / 最终分） | 评分层 | 量化任意代码改动对得分的影响 |

可观测性面的关键架构选择：

- **结构化而非纯文本**：所有产物都是 JSON / SVG，可程序化二次处理；
- **与控制流隔离**：观测字段不参与控制流裁决（如候选状态字段不参与投票），避免"日志变成隐式控制流"的反模式；
- **不依赖外部存储**：所有产物都落在隔离的运行目录下，离线可查、离线可对比。

这一维度让"调试"从"猜测式手动复现"变成了"看 trace + 看 DAG 图"的结构化分析过程，是这套架构能持续迭代优化的基石。

---

这些原则共同保证：在模型本身存在随机性、评测平台存在硬时间预算、任何深层调用都可能卡死的现实约束下，系统仍能给出**稳定、可解释、可调试、可恢复**的答案。
