# LangGraph Agent 拓扑架构详解

> 对应实现：`src/data_agent_baseline/agents/langgraph_agent.py`
>
> 本文只讨论**架构与设计动机**，不涉及代码细节、超参数、prompt 文本。

---

## 一、总览：这是一个怎样的 Agent

这是一个为 **DABench 数据分析 benchmark** 打造的、基于 LangGraph 的**严格 DAG 驱动多角色 Agent**。它在传统「ReAct = LLM ↔ Tools 自循环」的基础上，把任务执行显式拆成了「**先规划再执行**」的结构化流程：

- 一个 LLM 只负责**全局规划**（产出 DAG 计划）；
- 另一个 LLM 在**每个 DAG 节点的局部上下文**里负责执行（调工具、推进、提交）；
- 第三个 LLM 角色负责**最终答案审阅**；
- 上述三种"思考型"角色之外，还有一组**纯控制流节点**（调度器、重规划器、节点失败处理、空轮纠偏、终止节点）负责把它们串起来、做预算管控、做软重试与硬升级。

整体可以理解为一个 **Plan-Schedule-Execute-Reflect 闭环**，外加多层**预算守护**与**降级路径**。

---

## 二、拓扑结构：节点与角色

整个 Agent 是一张以 LangGraph `StateGraph` 编译出来的有向图，由 **9 类节点**组成。可以按"职责"划成 4 大类：

### 2.1 规划类（Planning Layer）—— 决定"做什么"

- **`planner`（初始规划器，LLM 节点）**
  整个图的入口。每个新任务只跑一次。它的工作不是回答问题，而是把"问题 + 数据集真实文件画像"翻译成一份**结构化的 DAG 计划**：若干个互相有依赖关系的子任务节点，外加一个被显式标注为"最终节点"的叶子。

- **`replanner`（重规划器，LLM 节点）**
  在执行过程中如果整个 DAG 卡住（没有可执行节点、又没全部完成）或某个节点彻底失败，会进到这里。它接收的不是"问题"本身，而是**"上一份失败计划 + 各节点状态 + 已有节点摘要 + 失败原因"**，被要求产出一份**避开同一个失败模式的新 DAG**。它独立于 `planner` 存在的关键意义在于：失败信息和原始问题是不同性质的输入，需要不同的提示与反思路径。

### 2.2 调度类（Scheduling Layer）—— 决定"现在做哪一个"

- **`scheduler`（DAG 调度器，纯控制流节点）**
  整张图的"心脏"。它**不调用 LLM**，只做四件事：
  1. 在当前 DAG 中挑出"依赖已满足、状态为 pending"的下一个就绪节点；
  2. 把该节点的目标、期望产物、上游依赖节点的"摘要"组装成一段**聚焦提示**注入到 executor 的对话上下文中；
  3. 检查终止条件（全部节点完成 → 走 reflector；卡住 → 走 replanner）；
  4. 重置 per-node 步数计数器、刷新可视化。

  设计动机：把"挑下一步做什么"从 LLM 的责任里**剥离出来**，变成确定性逻辑。这样既消除了 LLM 在多步任务中常见的"漫游 / 跳步 / 漏做"问题，又让上下文窗口可以始终保持精简。

### 2.3 执行类（Execution Layer）—— 决定"具体怎么做"

- **`executor`（执行器，LLM 节点）**
  绑定了所有数据分析工具（文件浏览、SQL、CSV/JSON/文档读取、SQLite Schema、Python 沙箱、列检查、答案提交、节点完成标记等）的 ChatLLM。它**只看到调度器给它的聚焦提示 + 之前几轮的对话**，专注于**当前一个 DAG 节点**的工作。完成时它会主动调用两类**控制流工具**之一：
  - 普通节点 → 调用 `mark_node_done`（带一段精炼摘要，给下游节点用）；
  - 最终节点 → 调用 `answer`（直接提交最终结果表）。

  这种"**让 LLM 用工具来宣布完成**"的模式，把状态机推进权显式交还给确定性代码（工具调用 → 路由器读到工具名 → 跳转），避免 LLM 通过自然语言模糊地"暗示"完成。

- **`tools`（LangGraph 标准 ToolNode）**
  执行 executor 上一轮发出的工具调用，并把结果以 `ToolMessage` 形式喂回对话。这是整张图里**唯一真正接触外部世界**的节点。

### 2.4 监督与降级类（Supervision & Fallback Layer）—— 决定"出问题怎么办"

- **`reflector`（反思器，LLM 节点）**
  在 executor 提交了 `answer` 之后被触发。它独立地检查"这个答案在结构、列数、行数、单位、空值、字符串大小写"等维度是否对得上问题。结论二选一：通过（`OK`）就走向终止；不通过（`RETRY`）就重置最终节点状态、回到调度器、让 executor 重新提交一次。重试有上限。

- **`node_failure`（节点软失败处理器，纯控制流节点）**
  当 executor 在单个节点内**消耗完该节点的步数预算**还没收尾，会进到这里。它做一次"软退避 vs 硬升级"的二分判断：
  - 如果该节点的累计尝试次数还没到上限 → 把节点状态退回 `pending`，让调度器再焦点一次（**软重试**，等价于"重新给它一次机会"）；
  - 如果累计尝试已经达到上限 → 把节点标 `failed`、设置重规划原因、走 replanner。

- **`nudge`（空轮纠偏器，纯控制流节点）**
  在某些 OpenAI 兼容模型（实测 Qwen via DashScope）会偶发输出"既无文本也无工具调用"的空 AIMessage。`nudge` 给它发一句明确的提醒（"你必须要么调工具、要么提交完成"），然后回到 `executor`。重提醒次数有上限，超过就直接终止。这是一个**只针对模型怪癖的轻量补丁层**，不消耗节点步数预算，避免无意义空轮把正常工具回合"挤出预算"。

- **`finalize`（终止节点，no-op）**
  纯结构性存在的叶子节点，唯一作用是把控制流接到 `END`。所有"放弃 / 通过 / 预算耗尽 / 反思满意"的路径都汇聚到它。

## 三、状态与数据流：信息是怎么流动的

整张图通过两层状态共同协作：

### 3.1 LangGraph 显式状态（`AgentState`）

这是一个由 `add_messages` reducer 累加的对话流，外加几个轻量计数字段：
- 对话消息流（系统提示 / 问题 / 聚焦提示 / AIMessage / 工具结果 / 各种软提醒）；
- 反思已用次数；
- 空轮纠偏已用次数；
- 当前节点已耗费的执行步数；
- 待重规划原因；
- 是否已最终化标志。

设计要点：把"对话历史"和"流程预算"放到同一份图状态里，让所有节点（包括路由器）都能基于它做确定性决策。

### 3.2 共享侧通道（`ToolRunContext` / `DAGRuntimeState`）

LangGraph 的 `ToolNode` 在调用工具时只能访问闭包里的对象，没法直接修改图状态。但 `mark_node_done` 和 `answer` 这两个**控制流工具**必须把信息写入"DAG 状态"和"最终答案"里。因此架构里专门设计了一个**侧通道对象**，由所有节点和工具共享：

- DAG 本身（节点列表 + final_node_id）；
- 每个节点的**状态**（pending / in_progress / done / failed）；
- 每个节点的**输出摘要**（被 `mark_node_done` 写入，被调度器在拼下游聚焦提示时读取）；
- 每个节点的**尝试次数**；
- 当前焦点节点 ID；
- 重规划次数；
- 一份完整的**事件审计日志**（用于 trace 重建和可视化）。

这种"图状态 + 侧通道"双层设计的动机是：**对话归对话，控制状态归控制状态**。把 DAG 的强类型状态从松散的消息流里独立出来，既方便调度器/工具做精确判断，也方便事后导出结构化 trace。

### 3.3 关键的"上游摘要传递"机制

每当调度器焦点一个新节点时，它**只**会把该节点**直接依赖**的若干上游节点的"完成摘要"嵌进聚焦提示——而不会把完整的对话历史、完整的中间数据、或者 transitive（间接）依赖也一并塞过去。

这是整个架构里最重要的**上下文工程决策**之一：

- **不传全部历史**：避免上下文爆炸、避免下游节点被无关细节干扰；
- **不传 transitive deps**：因为间接依赖的关键信息已经在直接依赖的摘要里被显式总结过；
- **传"摘要"而非原始数据**：强迫上游 LLM 把自己的工作产物**显式地命名 + 总结**，下游消费的是事实而非过程，能极大降低跨节点串扰。

代价是上游摘要的质量直接决定下游成败——所以系统在 prompt 层强约束了"摘要必须是事实性的、要包含具体路径/表名/数值"，并且在调度器侧加了"如果上游摘要里看不到任何文件路径形态的 token，就额外提醒下游先调 list_context"这种**启发式补救**。

## 四、控制流：路由器决定一切

LangGraph 的 conditional edges 让每个节点完成后都需要由**路由器函数**决定下一站。这套架构里有 7 个路由器，它们的存在让整张图能在"正常进展 / 软退避 / 硬升级 / 反思重试 / 重规划 / 终止"之间精确切换：

- **planner / replanner 之后** → 永远去 scheduler（规划完必走调度）。
- **scheduler 之后** → 四选一：有重规划原因则去 replanner（除非次数耗尽走 finalize）；全部完成且已有答案则去 reflector；全部完成但无答案则 finalize；否则就是正常焦点了一个新节点 → executor。
- **executor 之后** → 四选一：有挂起的工具调用就去 tools；既无工具又无文本（空轮）且 nudge 还有预算 → nudge；空轮但 nudge 也耗尽 → finalize；非空但节点步数耗尽 → node_failure。
- **tools 之后** → 四选一：刚调了 `answer` 且答案就位 → reflector；刚调了 `mark_node_done` → scheduler（推进下一个节点）；都不是但当前节点步数已耗尽 → node_failure；否则继续 executor。
- **node_failure 之后** → 二选一：还有重规划预算就回 scheduler（软重试同节点 / 或承接 failed 状态去 replan）；预算耗尽且确实有失败节点 → finalize。
- **reflector 之后** → 二选一：通过 → finalize；要求 RETRY → scheduler。
- **nudge 之后** → 直接回 executor（无条件，因为 nudge 本身已经只是一段提醒）。

**设计动机**：把状态机的迁移规则从 LLM 的"自由意志"里抽离出来，全部下沉成纯函数路由器。LLM 只决定"做什么内容"，**不决定"下一步去哪"**；下一步去哪由代码读"工具名 + 状态字段 + 计数器"决定。这是整个 Agent 行为可预测、可调试、可设上限的根本原因。

## 五、四层预算 / 安全网设计

整张图里**每一处可能"陷进去"的地方都有显式预算**，从内到外形成四层同心保护：

1. **单工具调用层：** 通过软提醒检测"连续 N 次相同参数的同一工具"（典型死循环模式）和"对同一份长文档过度分页 read_doc"（典型探索发散模式），在下一次 LLM 调用前注入一段一次性 SystemMessage 警告，引导模型换策略或提前提交。

2. **单节点层：** 每个 DAG 节点都有 `max_steps_per_node` 个 executor 回合的预算；节点本身还有 `max_node_attempts` 次"整轮重试"的机会。两者乘起来构成"一个节点最多能消耗的总 LLM 调用数"。预算用尽则降级到 node_failure，进而升级到 replanner。

3. **整体规划层：** `max_replans` 限制整个任务最多被重新规划几次。一旦重规划次数耗尽且仍有节点 failed，整个任务就 finalize（带失败原因）。

4. **整体反思层：** `max_reflections` 限制 reflector 最多让 executor 重交几次答案。

此外还有**动态节点步数上限**（dynamic step cap）：当 DAG 极简（≤2 节点）时上限放宽到 1.5 倍，依赖项多的节点每多一个依赖增加固定额度，最终节点再额外加少量额度——这是为"小 DAG 单节点天然要做更多事"和"汇总节点天然要交叉引用更多上游"提供的弹性。

设计动机：早期版本曾经因为"双层重试叠加 + 无 timeout 上限 + 无步数上限"导致单个 task 跑到 1800 秒撞死，现在的同心圆预算结构是从那次教训反推出来的——**任何一个 LLM 失败都不能让整体卡死，每一层都要有明确的兜底路径**。

## 六、抗幻觉的"前置数据画像"机制

planner 和 replanner 在被调用之前，都会先**离线地扫描任务的 `context/` 目录**，构建一份紧凑但具体的"数据集画像"：包括目录树、SQLite 库的真实表名 + CREATE TABLE 摘要、JSON 文件头、CSV 表头与首几行、Markdown/TXT 文件头。这份画像作为 HumanMessage 一并喂给 planner。

设计动机：在更早的版本里，约 80% 的失败都是 planner / executor**虚构了不存在的文件路径**（典型表现是问"data.db 在哪"，但目录里其实只有 JSON 文件）。把"真实存在的文件清单 + 它们各自长什么样"前置注入计划阶段，从源头压制了路径幻觉这一类失败。replanner 同样会拿到一份**最新的**画像——因为很多时候重规划的根因就是"路径错了"，必须基于事实重新出计划。

## 七、运行时治理与可观测性

- **重试隔离 by 调用点：** planner / executor / reflector 三种 LLM 调用对任务成败的影响差异巨大（planner 失败 = 全死；executor 失败 = 由外层兜底；reflector 失败 = 完全无伤）。架构上为它们配置了**差异化的重试预算与退避策略**，并对客户端 timeout 类异常**一律不重试**（重试同一个慢请求还是会慢），但服务器 5xx / 限流 429 会按 `Retry-After` 头精确退避。
- **DAG 实时可视化：** 每次 plan / replan / 节点状态变化、节点失败时都会触发一次 SVG 渲染（如果配置了输出目录），让调试者能在事后回放整张 DAG 是怎么演化的。
- **完整事件审计日志：** DAG 状态对象内置一个事件流（plan / replan / node_start / node_attempt_failed 等），最终被合成为 trace 的一部分。
- **trace 与对话流分离：** 架构层面区分"对话消息（用于 LLM 看）"与"步骤记录（用于人和评测系统看）"——后者是从前者 + 事件日志中重新组装出来的，确保即使 prompt 工程改变也不会破坏 trace 兼容性。

## 八、设计动机总览：为什么是这样一张图

可以把这个架构的全部设计动机归纳成 5 句话：

1. **把规划与执行解耦。** 让一个 LLM 通看全局产出 DAG，让另一个 LLM 在每个 DAG 节点里只看局部聚焦提示。这同时缓解了"上下文过长 → 模型注意力涣散"和"多步任务 → LLM 漏步跳步"两类问题。

2. **把状态机从 LLM 手里拿走。** 推进 / 终止 / 重试 / 重规划全部交给纯函数路由器和工具触发，LLM 只通过调用 `mark_node_done` / `answer` 这种**控制流工具**来"申请"状态迁移，不能用自然语言含糊地推进流程。

3. **把"中间产物"从对话里抽出来变成显式摘要。** 每个节点用一段精炼摘要喂下游，而不是把整段历史、整张表都塞过去。这是节点间协作能 scale 到 6 个子任务而不上下文爆炸的关键。

4. **每一层都有降级路径。** 工具死循环 → 软提醒；节点超步 → 软重试；节点彻底失败 → replan；replan 用尽 → finalize。整个图没有任何一个状态会陷在那里出不来。

5. **数据先于推理。** 让 planner 在落笔前就看到真实文件画像，用确定性的事实压制 LLM 的幻觉倾向；让 reflector 在最终交付前再做一次结构性体检，把"对了但格式错"的低级失败拦下来。

## 九、与传统 ReAct Agent 的关键区别

| 维度 | 传统 ReAct | 本架构 |
| --- | --- | --- |
| 任务分解 | 隐式（LLM 自己边想边做） | 显式（planner 先产出 DAG） |
| 状态推进 | LLM 用自然语言决定何时停 | 工具调用 + 路由器决定 |
| 上下文 | 单条不断膨胀的对话 | 每节点局部聚焦提示 + 上游摘要 |
| 失败恢复 | 通常无 | 三层（节点软重试 / replan / 反思 RETRY） |
| 预算控制 | 通常单一 max_steps | 节点级 / 任务级 / 反思级 / 重规划级四层独立 |
| 抗幻觉 | 依赖 prompt | 前置数据画像 + reflector 后置审阅 |
| 可观测性 | 仅消息流 | 消息流 + DAG 事件流 + DAG 实时 SVG |

这套架构本质上是把一个"通用 LLM Agent"折弯成了一个**针对数据分析任务做了大量定向加固的工业级流水线**，所有看起来繁琐的节点、路由器、计数器，背后对应的几乎都是过往某次具体的失败模式。
