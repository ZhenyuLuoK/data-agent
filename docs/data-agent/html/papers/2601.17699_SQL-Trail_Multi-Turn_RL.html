SQL-Trail: Multi-Turn Reinforcement Learning with Interleaved Feedback for Text-to-SQL

👥 Harper Hua, Zhen Han, Zhengyuan Shen, ..., Vassilis Ioannidis, Huzefa Rangwala（12 作者） 🏛️ Amazon AGI 📅 2026.01

把 Text-to-SQL 从"单步翻译"重新表述为"多轮交互推理"。 在 RL 训练框架中让 Agent 与 DB 真实交互（执行、看反馈、再修正）。两大关键设计： ① 自适应 turn-budget，按题目难度动态分配交互轮数； ② 复合 reward panel，同时激励 SQL 正确性与高效探索。 在 BIRD-SQL 等 benchmark 上设新 SOTA； data efficiency 高出单步 RL SOTA 最高 18×； 7B/14B 模型平均 超大私有系统 5%。

1. 核心问题与洞察

❌ 单步 Text-to-SQL 的固有瓶颈

① 缺乏迭代推理

人类专家面对复杂查询时，会反复"试探-观察-修正"：先看 schema、查几行数据、写一版 SQL、看错误信息再改。单步 LLM 一次性出 SQL，根本没机会做这种 iterative reasoning。

② 缺乏 schema 探索

真实 DB 有几十上百张表 + 几百列。专家会通过 SELECT col FROM table LIMIT 5 先看实际值再写。单步生成只能基于 schema 文本盲猜。

③ 缺乏 error-correction

SQL 写错（列名拼错、JOIN 条件不对、类型不匹配）后单步 LLM 没有机会改 —— 即使 CHESS / MAC-SQL 那种 self-refine 也只在生成阶段做一两轮，没融入 RL 训练目标。

④ 单步 RL 数据效率低

已有的 SQL-R1 等单步 RL 方法把"一步生成一条 SQL"作为训练单元，每条训练样本只能学一个 reward 信号；样本利用率有限。

✅ 核心洞察：把 Text-to-SQL 训成"多轮交互 RL agent"

SQL-Trail 把 SQL 生成视为 agent 与 DB 环境的 multi-turn 交互过程。每轮 agent 可以选择 ① 执行 SQL 看结果，② 探索 schema/sample 数据，③ 提交最终答案。 通过 RL 直接优化 agent 在整条交互轨迹上的行为，使其学会人类式的"试探-观察-修正"。 关键创新：自适应 turn-budget 让简单题快速结束、复杂题深入探索；复合 reward 同时奖励正确性与探索效率，避免无意义反复执行。

逻辑链路

NL Question → 🤖 Agent: think ↻ ⚙️ Execute / Probe DB ↻ 👀 Observe Feedback → ✅ Final SQL + Reward

2. 方法：Multi-Turn RL 框架

① 多轮交互范式

每一步 agent 输出一个 action：

  • Probe：执行探索性 SQL（查列、查样本、查 distinct 值）
  • Try：执行候选 SQL 看结果
  • Submit：提交最终答案

Action 后 DB 返回 observation（结果集 / 错误信息）。Agent 据此进入下一轮。

② Adaptive Turn-Budget Allocation

关键观察：BIRD 中题目难度差异极大（简单聚合 vs 多表嵌套）。固定 turn 数有两个问题：

  • 给简单题太多轮 → 浪费 compute、增加幻觉
  • 给难题太少轮 → 无法收敛

SQL-Trail 设计 自适应 budget 机制：根据问题难度动态决定该题最多探索几轮，使训练 / 推理 compute 更高效。

③ Composite Reward Panel

不是单一"对错 0/1"，而是多维度奖励：

  • Correctness reward：最终 SQL 执行结果是否正确
  • Efficiency reward：交互轮数是否经济（用 turn-budget 归一化）
  • Exploration reward：probing 是否带来真正信息增益

这个组合避免了 agent 学到"无脑反复试错"或"轻易 submit 错答案"两种 degenerate 行为。

④ Multi-Turn RL 训练

训练单元从"单条 SQL"升级为"完整交互轨迹"：

  • 每条 trajectory 给一个 reward 序列；
  • 用 PPO/GRPO 风格的多轮 RL 算法优化策略；
  • 共享相同的"问题-DB pair"在不同轨迹下能给出多个学习信号 → 数据效率比单步 RL 提升最高 18×。
设计哲学：把 Text-to-SQL 从 "NLP 翻译问题" 重新框定为 "agent 与数据库的交互推理问题" —— 这是与 CHESS、CHASE-SQL、XiYan-SQL（在推理时引入交互）相比，把交互直接放进训练目标的关键差异。

关键发现

  • Multi-turn > Single-pass：交互能让小模型显著缩窄与大模型的差距
  • Data efficiency 大幅提升：每条数据带来更多训练信号 → 训练成本下降
  • Adaptive turn-budget 重要：固定 budget 在简单题浪费、难题欠缺
  • 复合 reward 必要：单一 correctness reward 会出现 degenerate 行为（盲猜 / 无意义试探）

5. 多轮交互能解决的失败模式

基于 SQL-Trail 论文动机部分。

列值分布探查

当用户问"销量最高的 5 个类别"时，类别可能存在 category 列的某个枚举值集合。单步生成的 SQL 必须直接猜列名 + 写 GROUP BY；但如果 category 是层级的（"电子/手机/智能机"），需要先选粒度。

SQL-Trail 的 agent 可以先 SELECT DISTINCT category FROM ... LIMIT 20 看实际取值再决定 GROUP BY 字段。这种 schema exploration 能力是单步生成无法获得的。

多表 JOIN 路径选择

大 schema 中两张表可能有多条 JOIN 路径（直接外键 vs 经中间表）。哪条对当前问题更合适，需要看实际数据基数与索引情况。

Multi-turn agent 可以试不同 JOIN 写法，看返回行数 / 执行成功与否，选最合适的。这种"以执行结果验证假设"的能力是 SQL-Trail 与单步方法的本质差异。

从执行错误信息中学

错误信息（"column X does not exist", "ambiguous column"）含有正确做法的强信号。Multi-turn 训练让 agent 学会读错误信息，而单步方法只能依赖事后 self-refine。

SQL-Trail 的 reward 设计鼓励 agent 在"看到错误信息 → 给出修复"路径上获得正向激励，自然学会该行为。

6. 启发与未来方向

💡 设计哲学

  • Text-to-SQL 不是翻译，是交互推理
  • 把"试探"作为 first-class action
  • RL reward 必须是复合的，单一 reward 会被 hack
  • 训练分布要覆盖真实交互轨迹，不只是 (Q, SQL) pair

🚀 技术贡献

  • Multi-turn RL 框架的规范化设计
  • Adaptive turn-budget 机制
  • Composite reward panel 的工程实现
  • 验证小模型 (7B/14B) 通过交互可超大模型

🌍 实践影响

  • 对企业级 NL2SQL 部署有重要意义：私有 7B/14B 模型 + 多轮交互即可对标 GPT-4
  • 降低算力门槛，提升数据 efficient 训练的可能性
  • 启发后续工作（如 TRUST-SQL）继续在多轮 RL 方向深入

⚠️ 局限

  • 多轮训练的 wall-time 高于单步 RL（虽然 sample efficiency 好）
  • 真实 DB 交互需要 sandbox / safety guard，工程复杂度高
  • 对超大 schema (Spider 2.0 级) 的扩展性需要进一步验证
  • composite reward 的权重调参依然是 art，可能需要按 benchmark 调整
