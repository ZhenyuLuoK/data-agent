TQA-Bench: Evaluating LLMs for Multi-Table Question Answering with Scalable Context and Symbolic Extension

👥 Zipeng Qiu, Yujian Peng, Guanjie He, Bo Yuan, Chao Wang 📅 2024.11

为多表 QA 设计的新一代评测基准：聚焦"跨多表推理"+"可扩展上下文长度"+"符号化扩展"。 与 Spider/BIRD 关注 SQL 生成不同，TQA-Bench 直接评估 LLM 看到多张表后能不能给出正确答案， 是 TableQA / 数据 Agent 中一个高质量、可控难度的新尺子。

1. 研究空白与动机

❌ 现有 TableQA / NL2SQL benchmark 的不足

① 单表为主

WikiTableQuestions、TabFact 等多为单表。但企业现实是多表 JOIN。

② 上下文长度固定

几乎所有 benchmark 都把 schema/数据塞 prompt，但没人系统研究"上下文从 4K 到 128K"对推理的影响。

③ SQL vs QA 的混淆

Spider/BIRD 评估 SQL 生成正确性，但用户真正关心的是答案。SQL 错误但答案对、SQL 对但执行报错的情况都未充分讨论。

④ 数据规模的影响未测

表行数从 10 到 100,000 的影响如何？多数 benchmark 用固定规模。

✅ TQA-Bench 的核心创新

① 多表场景：所有任务涉及 2 个或更多表的 JOIN/聚合；
② 可扩展上下文：每个任务可以以不同上下文长度（短/中/长）呈现，方便研究 long context 能力；
③ 符号化扩展（Symbolic Extension）：把数据替换为不同规模/分布的"符号化"版本，控制语义一致但难度不同；
④ 直接 QA 评估：给定问题与表，直接对答案评分，绕过 SQL 形式。

逻辑链路

真实多表数据 → 问题模板生成 → 符号化扩展（控制规模） → 多上下文呈现（4K~128K） → LLM 直接答 → 评分

2. Benchmark 构建

① 数据源

  • 开源关系数据库 schema（如 BIRD-style 数据库）
  • 含真实业务关系的多表场景
  • 覆盖事实表 + 维度表的常见 JOIN 模式

② 问题模板

  • 聚合（SUM / AVG / MAX）
  • 过滤 + 聚合（多条件 WHERE）
  • 多表 JOIN 后的统计
  • 嵌套查询（top-k / 排名）

③ Symbolic Extension

核心创新：基于一个"种子"问题，可以系统化生成不同行数、不同分布的等价问题。

例如：原表 100 行 → 扩展到 1k / 10k / 100k 行；问题语义不变，但数据规模和上下文压力大不同。

④ 上下文压缩 vs 完整

同一问题，提供：

  • 仅 schema（无数据）
  • schema + 抽样数据
  • schema + 完整数据（dump 进 prompt）

3. 评估框架

对比模型

  • GPT-4o、GPT-3.5
  • Claude-3.5-Sonnet
  • 开源 LLM（Llama-3、Qwen 等）

评测设置

  • 多种上下文长度（4K / 16K / 64K / 128K）
  • 多种数据规模（10 行 → 10k 行）
  • End-to-End QA（答案匹配）

4. 实证发现

论文报告的关键定性发现

基于 TQA-Bench 论文（arXiv:2411.19504）实验章节与第三方 reproduction（arXiv:2505.07453）：

  • 上下文长度的悬崖效应：在多数 LLM（Llama-3.1、Qwen-2.5、Mistral、DeepSeek-R1）上，当输入超过 ~4K token 时准确率显著下降；唯一例外是 GPT-4o-mini 在 4K 后仍保持相对稳定。
  • 表数量的负面影响：从 2 表 → 5 表 → 8 表，准确率呈梯度下降；多数模型在 ≥5 表场景上接近随机基线。
  • 聚合算子越复杂越难：MAX / MIN / 简单 SUM > 多条件 AVG / 占比类 > 多表 JOIN 后聚合 > top-k 嵌套。
  • "NL2SQL + 执行"普遍胜过"直接表-QA"：当 LLM 自己生成 SQL 并执行时，准确率明显高于把全表数据塞进 prompt 让其推理；TQA-Bench 论文在结论中明确把这作为推荐 pipeline。
  • 符号化扩展的泛化测试：同一问题语义下，把表行数从 100 扩到 10k，多数 LLM 准确率显著下滑，表明并非真正"理解"关系，而是在小数据上"看穿"了答案。

注：TQA-Bench 论文报告了多种 LLM × 多种 context 长度 × 多种规模的完整数字矩阵；此处不复制具体单点分数，避免在任何一个组合上误读。详见原文 Section 5（Experiments）。

5. 启发与未来方向

💡 Benchmark 设计哲学

  • "可控规模"是评估 long-context 必备维度
  • QA 而非 SQL：聚焦最终用户价值
  • 符号化扩展：从语义不变出发探究规模影响

🚀 实践影响

  • 验证了"NL2SQL → 执行"在多表 QA 上的鲁棒性优势
  • 给 Data Agent 设计提供"何时该写 SQL，何时该把数据塞 prompt"的依据

🌍 后续工作

  • 已被多个表 QA / Data Agent 工作引用为标准评测
  • 启发了 OpenDataBench、TReB 等更细粒度的 benchmark

⚠️ 局限

  • 大表完整 dump 到 prompt 在生产几乎不可行（成本/限长）
  • 问题模板覆盖有限，可能不充分覆盖真实分析需求
  • 未涵盖中文 schema 与中文问题
