XiYan-SQL: A Multi-Generator Ensemble Framework for Text-to-SQL

👥 阿里巴巴 XGenerationLab Team 🏛️ Alibaba Group 📅 2025.07

1. 核心问题与洞察

❌ 工业落地中纯学术方法的不足

① Schema 表征过于单薄

仅用 CREATE TABLE 文本（DAIL-SQL/CHESS 风格）丢失了大量企业元信息：列描述、典型值、外键关系、业务约束等。

② 单一生成器的"风格盲区"

纯 ICL 路线（GPT-4 + few-shot）和纯 SFT 路线（自有 NL2SQL 模型）各有强项，单选其一都会丢分。

③ 候选数 vs 多样性的悖论

采样越多 token 越贵，但若候选高度相似（即缺少多样性），则 selection 模块可选择的解空间被压缩。论文动机：需要"智能多样化"（多样的生成路径与生成器）而非"暴力多采样"。

④ 工业方言/dialect 不友好

BIRD 是 SQLite，但企业大多用 MySQL/PostgreSQL/Snowflake/Hive，方言迁移损失大。

✅ 核心洞察：用 M-Schema 喂饱模型 + ICL/SFT 双路并发 + 强 Selector 把关

① 把 schema 升级为多模态信息容器（列名 + 类型 + 描述 + 典型值 + 关系）；
② 同时使用 In-Context Learning 路线（强模型 + 精选示例）和 Supervised Fine-Tuning 路线（自训练 XiYanSQL-QwenCoder），二者错峰互补；
③ 用专门训练的 Selection Model 在候选间打分，不依赖 self-consistency。

逻辑链路

问题 + Raw Schema → 📋 M-Schema 构建 → 🎯 Schema Filter ⤵ 🤖 ICL 生成器 + 🎓 SFT 生成器 → 🔧 Refiner（执行反馈） → 🏆 Selection Model → 最终 SQL

2. 方法：M-Schema + 多生成器集成

M-Schema：多维度的 schema 增强

区别于只把 schema 序列化为 CREATE 语句，M-Schema 在每张表/列上携带：

  • 名称 + 类型 + 主外键（基础结构）
  • 列描述（来自 DDL 注释或元数据系统）
  • 典型值 (sample values)（解决"frequency 列实际是月/季度对账周期"这类问题）
  • 关系标注（A.x 与 B.y 是同一实体的不同别名）
  • 业务约束（如"金额需为正"）

论文证明 M-Schema 是 XiYan-SQL 准确率提升的关键来源之一，相关代码已开源。

ICL（In-Context Learning）生成器

使用强模型（GPT-4 / Claude / 专有大模型）+ 动态示例选择。示例选择策略沿用 DAIL-SQL 的 SQL skeleton 相似度，但在 M-Schema 表征下能找到更精准的语义匹配。

该路径的优势：复杂、跨领域、罕见语法的 SQL 生成质量高。

SFT 生成器：XiYanSQL-QwenCoder

基于 Qwen2.5-Coder 架构，用大规模合成的 NL2SQL 数据（含多方言、思维链、纠错轨迹）SFT 训练。

该路径的优势：在常见模式（聚合、JOIN、WINDOW）上稳定且推理成本低；对多方言（MySQL/PG/Snowflake）泛化更好。

开源版：XGenerationLab/XiYanSQL-QwenCoder。

Selection Model：候选选择器

训练一个独立模型对"问题 + schema + 候选 SQL + 执行结果"打分。考虑维度：

  • SQL 是否能成功执行
  • 结果是否非空、是否合理（行数/列数）
  • SQL 与 schema 的 fit 程度
  • 同一组候选的相对优劣

对比 self-consistency 多数投票，Selection Model 在多样化候选场景中有显著优势。

设计哲学：XiYan-SQL 不追求"一个万能生成器"，而是构造"互补的生成池 + 强判别器"。这是一种典型的工业 ensemble 思路：多样性 × 鉴别力 = 综合效果。

消融研究

  • 仅用 ICL 生成器：在罕见 schema 上稳定，但常见模式有"风格漂移"
  • 仅用 SFT 生成器：在常见模式高效，但复杂跨域查询有上限
  • ICL + SFT 集成 + Selection Model：综合最优，集成增益显著
  • 去掉 M-Schema（仅用 CREATE TABLE）：BIRD-dev 明显下降，因为模型无法理解列语义

5. 案例研究

M-Schema：携带语义元信息的 schema 表征

论文比较了 M-Schema 与 CREATE TABLE 文本表征。M-Schema 在普通 DDL 之外额外携带：

  • 列描述（业务语义、单位、约束）
  • 典型/枚举取值（来自数据采样或字典）
  • 表/列之间的主外键关系强化标注
  • 用 markdown / 结构化格式呈现，便于 LLM 解析

论文消融显示，在保留同样的生成与选择策略下，M-Schema 相比 CREATE TABLE 风格在 BIRD 上有稳定增益 —— 尤其是在含枚举列、缩写列名的题上差距明显。这是 XiYan-SQL 整套系统的"地基"。

ICL × SFT 的互补性

论文设计中两路生成器各有长处：

  • SFT 生成器：在大规模 SFT 数据上训练（含 BIRD/Spider 风格），常见模式（聚合、JOIN、WINDOW）稳定，token 成本低，多方言泛化好；
  • ICL 生成器：用更强的 LLM + few-shot，对罕见结构（LATERAL、复杂 CTE、跨域 schema）更鲁棒。

Selection Model 综合 schema 适配度 + 执行可行性，从两路候选中挑出最佳版本，相比单路或简单 self-consistency 在 BIRD 上有持续增益。

Selection Model：多样候选下的稳健选择

论文 Section 3.4 / 4.3 强调：当候选池高度多样（同一题写法差异大但都执行成功）时，self-consistency / majority vote 容易选到"流行但错"的版本。

XiYan-SQL Selection Model 的设计：

  • 把 schema 适配（候选 SQL 引用的列是否在 sub-schema 中）作为关键特征；
  • 把执行结果 metadata（行数是否合理、列类型是否符合问题）作为信号；
  • 训练判别器学习"哪个候选更可能正确"，而非"哪个候选最常见"。

论文实测在多样化候选场景中显著优于 majority vote。

6. 启发与未来方向

💡 设计哲学

  • Schema 是新的特征工程：M-Schema 极大拓宽了 NL2SQL 上下文
  • ICL × SFT 集成：互补优于单选
  • 判别器值得专门训练（与 CHASE-SQL 同思想）

🚀 技术贡献

  • M-Schema 表征范式（已被多家企业系统借鉴）
  • 开源 XiYanSQL-QwenCoder 系列模型
  • 开源 NL2SQL MCP 服务器，可与 Claude Desktop / Cursor 直接集成

🌍 实践影响

  • 阿里云 DAS / Quick BI 的 NL2SQL 后端参考其架构
  • 多家国内企业落地直接使用 XiYanSQL-QwenCoder
  • 是国内 NL2SQL 领域影响最大的开源项目之一

⚠️ 局限

  • 多生成器集成 → 推理成本和延迟较高（多采样 + 多模型）
  • SFT 生成器需要大规模高质量训练数据
  • Spider 2.0 / 千列 schema 等极端场景仍有差距
  • Selection Model 的训练数据成本不低
