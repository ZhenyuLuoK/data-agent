MAC-SQL: A Multi-Agent Collaborative Framework for Text-to-SQL

👥 Bing Wang, Changyu Ren, Jian Yang, Xinnian Liang, Jiaqi Bai, Linzheng Chai, Zhao Yan, Qian-Wen Zhang, Di Yin, Xing Sun, Zhoujun Li 🏛️ 北航 + 腾讯 📅 2023.12（v6: 2025.03）

1. 核心问题与洞察

❌ DIN-SQL 等单 LLM Pipeline 的局限

① Schema 太大塞不下

BIRD 中很多 DB 包含 50+ 张表、上千列。DIN-SQL 直接把整个 schema 塞 prompt，超 token 限制或注意力稀释。

② "一次推理"难以覆盖复杂逻辑

嵌套查询 + 多 JOIN + 聚合 + 外部知识，单步 CoT 容易跳步出错。

③ 错误反馈未被利用

SQL 执行失败时，错误信息（语法错、列不存在、类型不匹配）是宝贵信号，但 DIN-SQL 仅用静态 self-correction，不真正执行。

④ 没有"职责-提示对齐"

同一个 LLM 在 prompt 内同时承担"找列、分类、生成、纠错"多重角色，相互干扰。

✅ 核心洞察

把 NL2SQL pipeline 中的每个职责显式分配给一个独立的 LLM Agent，让它们用自然语言协作： "专人专事 + 工具反馈 + 多轮迭代"，比单 LLM 端到端更鲁棒。

这是 NL2SQL 领域第一次把"agent-as-role"思想引入，启发了后续 CHESS、CHASE-SQL 的"多 Agent 集成"路线。

逻辑链路

User Question + Full Schema → 🎯 Selector Agent: 压缩 schema → 🧠 Decomposer Agent: CoT 拆子问题 → 🔧 Refiner Agent: 执行→错误→修正 ↺ 最多 K 轮迭代 → 最终 SQL

2. 方法：三 Agent 协作架构

Selector Agent：压缩 schema

目标：从一个可能含 50+ 表、千列的 DB 中抽取与问题相关的 sub-schema，使 prompt 在 token 限制内仍信息密度高。

策略：

  • 把 schema 序列化为 CREATE TABLE 风格
  • 用 GPT-4 阅读"问题 + 完整 schema"，输出"必要表/列"清单
  • 对超大 schema（>25 表），分批喂入 Selector，最后求并集

关键设计：Selector 给的是"宁多勿少"的表/列清单（recall > precision），由后续 Decomposer 自然地"用啥取啥"。

Decomposer Agent：分而治之

对简单问题：直接生成 SQL。

对复杂问题：用 CoT 把问题拆成子问题序列：

Q: "What is the average age of male teachers in schools where 
   the most expensive math textbook is published by Pearson?"

Sub-Q1: 找 Pearson 出版的最贵数学课本所在学校
Sub-Q2: 在这些学校中找男教师
Sub-Q3: 计算他们的平均年龄

每个 Sub-Q 单独生成一段 SQL，最终组合成嵌套查询或 CTE

关键设计：Decomposer 输出的不仅是"最终 SQL"，还包括"中间 SQL 推理链"，方便 Refiner 在某一步出错时局部修复。

Refiner Agent：执行反馈循环

核心：真正在数据库上 EXECUTE 生成的 SQL，根据反馈类型采取不同纠正策略：

反馈类型动作
语法错把错误信息回填给 LLM 让其修复
列/表不存在回到 Selector 扩展 schema
结果为空集重审 WHERE 条件、JOIN 关系（"软错误"）
类型不匹配检查 cast/compare 操作
正常返回停止迭代，输出 SQL

最多 K=3 轮迭代（论文实验 K=3 即可收敛）。

SQL-Llama（开源 SFT 模型）

论文同步开源 SQL-Llama-7B：用 MAC-SQL 框架在大量 BIRD/Spider 训练集上自动生成"问题 + 子问题 + SQL"轨迹，再用这些轨迹 SFT 一个 Code-Llama-7B。

结果（论文 Table）：MAC-SQL + SQL-Llama(7B) 在 BIRD-dev 达到 43.94% EX、57.36 VES；接 Oracle Schema 时 BIRD-dev 升至 51.43% EX、58.24 VES。证明 MAC-SQL 框架的"教师-学生蒸馏"路径可行，是当时同尺寸开源模型有竞争力的成果。

设计哲学：MAC-SQL 把 DIN-SQL 的"模块"升级为"Agent"。区别在于：模块是单线程、Agent 间通过自然语言对话；Refiner 真正与执行环境交互（DIN-SQL 仅 LLM 自我审视）。

消融研究（论文 §5）

论文按"逐 Agent 去除"做消融，证明三 Agent 各自贡献：

  • 去掉 Selector（直接喂全 schema）：在大型 BIRD DB 上准确率显著下降，且推理 token 数飙升
  • 去掉 Decomposer（一步直出 SQL）：嵌套查询的执行成功率明显下滑
  • 去掉 Refiner（无执行反馈）：语法错和列名错没机会被修复

注：上述定性结论来自论文消融小节；具体数值因不同 LLM/版本略有差异，详见论文 Table。关键发现：在大型 schema 场景下，Selector 收益最大；在复杂查询上 Decomposer/Refiner 收益更大。

5. 三 Agent 协同的失败模式覆盖

基于论文 Section 3（Method）与 Section 4（Experiments）的设计动机，三个 Agent 各自针对 NL2SQL 的一类典型失败模式，下文按模式而非具体题目展开。

Selector 应对的失败模式：schema 太大 / 噪声列干扰

BIRD 的部分库含数十张表、数百列，全 schema 一次性塞 prompt 既超 token 限制，又因无关列干扰让 SQL 生成器选错 JOIN/WHERE 列。

论文 Selector 的设计：

  • 对每个问题动态裁剪出包含必要表/列的子 schema；
  • 策略偏 recall（保守保留候选列），把 precision 留给后续 Decomposer；
  • 论文 Section 4 消融显示，移除 Selector 在大型 BIRD DB 上准确率显著下降，且 token 消耗飙升 —— 是 MAC-SQL 在大 schema 场景下的关键收益来源。

Decomposer 应对的失败模式：嵌套 / 多步推理

包含子查询、HAVING、UNION/EXCEPT 等的复杂查询，单步 prompt 难以一次写对。

论文 Decomposer 的设计：

  • 把复杂问题拆解为若干"子问题 + 子 SQL"，以 Chain-of-Thought 方式逐步生成；
  • 每个子步骤都基于 Selector 给出的精简 schema；
  • 论文消融显示移除 Decomposer 主要拖累嵌套查询难度子集的表现。

Refiner 应对的失败模式：执行期错误 / 列名不存在 / 类型不匹配

SQL 生成阶段语法看似合理，但实际执行可能因列名拼写、类型 cast、空表/越界等原因失败。纯 self-review（如 DIN-SQL 的 Self-Correction）无法拿到执行端真实信号。

论文 Refiner 的设计：

  • 真正在 DB 上执行 SQL，捕获错误码 / 错误消息 / 空结果；
  • 把这些反馈作为"工具结果"喂回 LLM 触发再生成；
  • 这种"执行驱动"的纠错被几乎所有后续 NL2SQL 工作（CHESS、CHASE-SQL、XiYan-SQL、Agentar）继承。

6. 启发与未来方向

💡 设计哲学

  • Agent = 模块 + 角色 + 工具反馈
  • Selector recall > precision：宁多勿少
  • 执行反馈 > 自审视：真正跑一下比 LLM 自己想强

🚀 技术贡献

  • NL2SQL 多 Agent 范式开创者
  • SQL-Llama-7B 是最早的开源 NL2SQL agent SFT 模型
  • 引入"执行反馈循环"，被几乎所有后续工作继承

🌍 影响

  • COLING 2025 收录
  • 启发了 CHASE-SQL、XiYan-SQL 的多生成器思想
  • 开源后被工业界（PingCAP、Snowflake、阿里云）参考

⚠️ 局限

  • 三 Agent 全用 GPT-4，推理成本高（每问 ~3 次 API 调用）
  • Selector 在千列 schema 上仍可能漏列 → CHESS 改进
  • 无候选生成与排序 → CHASE-SQL/XiYan-SQL 补足
  • 无交互能力 → BIRD-Interact 评估暴露问题
