Agentar-Scale-SQL: Advancing Text-to-SQL through Orchestrated Test-Time Scaling

👥 Ant Group Agentar Team 🏛️ 蚂蚁集团 📅 2025.09

蚂蚁集团出品、当前 BIRD 排行榜第一名的 NL2SQL 系统： 把 Test-Time Scaling (TTS) 思想系统化引入 NL2SQL， 用编排式 (Orchestrated) TTS 把多种推理时计算策略组合起来， 在 BIRD 测试集达到 81.67% EX / 77.00 R-VES，与人类专家基线 92.96% 仅相差 11.29pt。

1. 核心问题与洞察

❌ 单点 TTS 已触顶

① 单一 TTS 维度收益边际递减

仅靠多采样、self-consistency、CoT 这一类单一维度的"加大算力"，BIRD test 在 73-75% 附近反复徘徊。

② 多策略缺乏统一编排

CHASE-SQL（多 CoT 策略）、CHESS（候选生成 + UT）、XiYan-SQL（ICL+SFT 集成）各自有效，但互不知晓，简单拼装会产生重复算力浪费。

③ 自纠错与候选选择脱节

常见做法把 Self-Correction 和 Candidate Selection 当两个独立步骤，没有统一的"算力分配 + 终止"策略。

④ 工程系统级优化缺失

真实生产中 token 预算、延迟、可重复性都是硬约束。学术单点方法很少把"在固定预算下选最优策略组合"形式化。

✅ 核心洞察：Orchestrated Test-Time Scaling

把不同 TTS 策略（多生成器、多 CoT 路径、迭代纠错、候选选择）看作 orchestrator 可调度的"算力单元"。在每个 query 上，根据问题难度、当前候选质量、剩余预算，动态决定下一步用哪种 TTS 策略。

这把"NL2SQL 性能 ↔ 测试时算力"的关系从"单一维度的 scaling law"升级为"多维 orchestration 的 scaling law"。

逻辑链路

问题 + Schema → 🧠 Orchestrator（策略调度） ⤵ 多 CoT 路径生成 + 多生成器集成 + 迭代纠错 → 🏆 候选选择 (Critic) → 最终 SQL

2. 方法：编排式 TTS

论文把 TTS 的"算力维度"明确划分并组合：

① 多路径推理（Multi-Path Reasoning）

沿用 CHASE-SQL 的多 CoT 策略，同时采用 Divide-and-Conquer / Chain-of-Query / Schema-aware 等不同思维路径。

② 多生成器集成（Multi-Generator Ensemble）

同时使用闭源大模型 + 自训练 SFT 模型 + 不同温度的采样，提升候选多样性。

③ 迭代纠错（Iterative Refinement）

对每个候选 SQL 执行 → 收集错误/空结果 → 用专门的 Critic Agent 给反馈 → 改写。最多 K 轮。

④ 候选选择（Critic-based Selection）

训练偏好优化的 Selector，综合 SQL 结构、执行结果、schema fit 等多维度打分。

⑤ 大规模合成数据训练

团队用 LLM 自动合成大量 (问题, schema, SQL) 训练对，尤其涵盖 BIRD 风格的脏数据 + 外部知识场景，用于训练自家 SFT 生成器和 Critic 模型。

⑥ Orchestrator 调度

Orchestrator 不是简单流水线，而是带预算/置信度感知：在简单题上节省算力，在难题上 burn more compute。

设计哲学：把"测试时计算"作为一种显式的可调度资源而非"采样数 N"这一种维度。这与 OpenAI o1 / Google Gemini Thinking 把 reasoning 当成可分配资源的思想一致。

消融分析（论文 Section 4.4 定性结论）

论文系统消融了 Orchestrated TTS 的关键组件。报告的趋势：

  • w/o SQL selection scaling：用 self-consistency（majority voting based on execution results）替代偏好选择，EX 显著下降 → 证明 selector 是关键
  • w/o multi-generator：单生成器候选多样性不足，selector 上限受限
  • w/o iterative refinement：缺少基于错误反馈的迭代修正，复杂题失败率上升
  • 完整 Orchestrated TTS 才达到 BIRD test 81.67% EX

具体逐组件 EX 数字详见 Agentar-Scale-SQL 论文 v3 Section 4.4。

5. 案例研究

难度感知的算力分配（Orchestrator）

论文 Orchestrator 模块的核心思想：把 test-time compute 视为可调度的资源，根据 query 的初始难度信号（如初版 SQL 的执行成功率、生成器之间的一致性）动态决定：

  • 启用几个 generator
  • 每个 generator 采样几个 candidate
  • 是否进入迭代 refinement / pairwise selection

实现的语义：易题快速收敛，难题给足预算，把 token 投入精准匹配到收益最大的 query 上 —— 这是论文定义的 "Orchestrated Test-Time Scaling"。

合成数据 + SFT 生成器（论文 Section 3.3）

论文承认 BIRD 测试集对"含 external evidence、脏数据、列名缩写"的题占比远高于训练集分布。Agentar 团队的应对：

  • 用 LLM 自动合成带 evidence 字段、缩写列名、enum 取值约束的训练样本
  • 在合成数据上 SFT 一组 SQL 生成器与 critic
  • 训练后的模型在 BIRD test 上比纯 prompt 基线显著更稳

这是 Agentar 能够在 BIRD test 接近人类专家的关键工程因素之一。

论文报告的关键对比维度

论文 Table 1 和 leaderboard 上对比了多个 NL2SQL 系统在 BIRD test 上的 EX 与 R-VES。核心定性结论：

  • Agentar-Scale-SQL 报告 BIRD test 81.67% EX / 77.00 R-VES，距 human expert 92.96% 缩窄
  • 领先于 CHASE-SQL + Gemini（73.0%）、XiYan-SQL（75.63%）等学术 SOTA
  • 与同期工业方案（Distyl、AskData + GPT-4o）处于同一梯队

6. 启发与未来方向

💡 设计哲学

  • TTS 是新的 scaling 维度，且应被"编排"而非堆砌
  • 合成数据 + 偏好优化 是解决 BIRD 这类"长尾分布"benchmark 的关键
  • 难度感知预算是工业落地的必需

🚀 技术贡献

  • BIRD 榜首（81.67% EX）
  • 开源 Agentar-Scale-SQL 仓库
  • 系统化的 TTS 编排方法论

🌍 实践影响

  • 蚂蚁内部 Agentar 平台核心能力
  • 把 NL2SQL 推到"接近人类专家"的实用水准
  • 验证了"工业 + 学术 hybrid"路径的有效性

⚠️ 局限

  • 多策略 + 多模型 + 多轮 → 推理成本是 baseline 的 10×+
  • BIRD 仍然只是基准；Spider 2.0 / 真实企业场景差距仍大
  • 合成数据可能引入 bias（论文承认）
  • 开源版相比内部版有功能差异
