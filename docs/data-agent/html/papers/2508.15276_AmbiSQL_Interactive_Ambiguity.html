AmbiSQL: Interactive Ambiguity Detection and Resolution for Text-to-SQL

👥 Zhongjun Ding, Yin Lin, Tianjing Zeng, Rong Zhu, Bolin Ding, Jingren Zhou 🏛️ 阿里巴巴（XiYan-SQL 团队） 📅 2025.08 · SIGMOD 2026 Demo

把"用户问题歧义"作为 NL2SQL 的一等公民问题。 AmbiSQL 是首个把歧义检测 + 交互式消歧系统化的 demo： 自动发现自然语言查询中的潜在歧义， 用直观的多选题引导用户澄清意图，再 rewrite 为无歧义查询喂给 NL2SQL backend。 提出细粒度歧义 taxonomy（区分来自 DB 元素与来自 LLM 推理的歧义）。 论文报告：在歧义查询数据集上达到 87.2% 歧义检测 precision，并显著提升 SQL exact match。 与商业版 XiYan-SQL 集成，SIGMOD 2026 现场参会者可使用 40 个真实歧义查询体验消歧效果。

1. 核心问题与洞察

❌ 用户问题本身就有歧义

① "近期"是多近？

"列出近期销售额最高的客户"——"近期"是一周、一月还是一季度？不同选择对应完全不同的 SQL。

② "顾客"指哪张表？

DB 中可能同时有 customer、buyer、account_holder 三张相关表。NL 中"顾客"具体指哪个？

③ "销售额"如何聚合？

是按订单金额求和、按净收入计算（含退款）还是按毛收入？不同业务定义指向不同列与公式。

④ LLM 自我消歧不可靠

LLM 默认会"猜一个最常见的解释"，但这个猜测对当前用户而言可能是错的；且 LLM 不主动告知自己做了什么假设，用户不知道结果是怎么来的。

✅ 核心洞察：把"消歧"显式做成交互式步骤

AmbiSQL 把 NL2SQL 重新组织为： 歧义检测 → 多选题问用户 → 收集反馈 → 重写问题 → 调 NL2SQL backend。 关键创新有两点： ① 细粒度歧义 taxonomy，区分歧义的来源 —— 既包括来自 DB 元素的歧义（多张相关表 / 多个语义近似列 / 字面值不一致）， 也包括来自 LLM 推理的歧义（隐式假设、聚合粒度选择、时间范围解释）； ② 多选题驱动的 UI，让消歧门槛足够低 —— 用户只需点选项，不必再写 NL。 与商业版 XiYan-SQL 集成证明该路径在工业级系统中是可行且必要的。

逻辑链路

用户 NL 提问 → 🔍 歧义检测 → 📋 多选题澄清 → ✍️ Rewrite 无歧义查询 → 🤖 XiYan-SQL Backend → ✅ SQL + 结果

2. 方法：歧义检测与交互式消歧

① Fine-grained Ambiguity Taxonomy

论文把 NL2SQL 中的歧义按来源细分为两大类：

  • DB-element ambiguity：歧义源自数据库本身
    • 表选择歧义（多张相关表）
    • 列选择歧义（语义近似列）
    • 字面值匹配歧义（大小写、缩写、拼写）
    • JOIN 路径歧义（多条可达路径）
  • LLM-reasoning ambiguity：歧义源自 LLM 推理过程的隐式选择
    • 聚合粒度（按天/周/月）
    • 时间范围解释（"近期"="?"）
    • 排序依据（按某 metric 还是按时间）
    • 过滤条件强弱（包含 NULL 否）

② 自动歧义检测

对一个 NL 问题，AmbiSQL 检测是否存在以上 taxonomy 中的某类歧义：

  • 结合 schema metadata（哪些表 / 列名相近）；
  • 结合 LLM 对问题潜在解释的多样化采样；
  • 当多种合理解释存在时，标记为歧义。

③ 多选题生成

对每个检测到的歧义点，AmbiSQL 生成多选题：

  • 问题文字直白描述歧义点（"您说的'顾客'是指..."）；
  • 选项是 taxonomy 引导下的有限可选解释；
  • UI 上以多选 / 单选呈现，用户只需点击。

关键：选项必须可枚举且互斥，避免 open-ended 让用户负担过大。

④ Question Rewriting

收集用户回答后，AmbiSQL 把澄清信息融合回原问题：

  • 例：原问题 "近期销售额最高的顾客" + 用户选择"近期 = 最近 30 天" + "顾客 = customer 表"；
  • 生成 rewrite 后的查询："最近 30 天 customer 表中销售额最高的顾客"；
  • 送入 XiYan-SQL backend 生成 SQL。

这一步保证下游 NL2SQL 拿到的是消歧后的清晰问题，避免它再做隐式假设。

⑤ 与商业 XiYan-SQL 集成

论文 v2 明确说明 AmbiSQL 已集成到阿里 XiYan-SQL（同团队的商业 NL2SQL 系统，2507.04701）作为前端消歧层。整体流程：

  1. 用户在前端提问 → AmbiSQL 检测歧义；
  2. 若有歧义，弹出多选题；用户点选；
  3. AmbiSQL rewrite 后的问题进入 XiYan-SQL：M-Schema + 多生成器 + Selection Model；
  4. 返回 SQL + 执行结果 + （可选）歧义解决路径解释。

这是学术研究 → 工业产品闭环的代表性范式：把 demo 直接接到生产 NL2SQL pipeline 之上。

设计哲学：把 NL2SQL 失败的一大类原因（"用户没说清"）从"算法问题"转化为"UX 问题" —— 与其让算法猜，不如让用户选。这条路线对工业产品落地极其务实。

5. AmbiSQL 覆盖的歧义模式

基于论文 taxonomy 设计动机。

多张相关表 / 多列同义

当 DB 中有 customer、buyer、account_holder 三张相关表时，"客户"指哪张？或同一表下 revenue、net_revenue、gross_revenue 三个列时，"销售额"指哪个？

AmbiSQL 处理：

  • 检测：schema 上语义相近的表/列
  • 多选题：列出候选表/列 + 简要说明（如"net_revenue：扣除退款后的净收入"）
  • 用户点选 → rewrite 时把具体名称固化进问题

字面值不一致

用户问"销售额最高的省份"，但 DB 里 province 列存的是英文缩写。AmbiSQL 可结合 LSH 风格匹配（CHESS 思想）发现潜在不一致。

多选题示例：

  • 选项 A：DB 中包含 "Beijing", "Shanghai" 等英文全称
  • 选项 B：DB 中包含 "BJ", "SH" 等缩写

用户选择后，AmbiSQL 在 rewrite 时插入正确字面值形式。

聚合粒度 / 时间范围

"列出近期销售额最高的客户"中：

  • "近期"歧义 → 多选题：最近 7 天 / 30 天 / 90 天 / 本季度 / 本年度；
  • "销售额"是订单数 vs 订单金额 vs 净收入 → 多选题枚举；
  • "最高"是 TOP 1 还是 TOP K → 多选题。

这种隐式假设在传统 NL2SQL 里完全由 LLM 自行决定，AmbiSQL 把它暴露给用户。

6. 启发与未来方向

💡 设计哲学

  • 用户问题本身可能是错的根因，不能全推给 NL2SQL 算法
  • 消歧应该是 NL2SQL 系统的第一类公民，不是 afterthought
  • UX 比算法更能解决"问题模糊"问题：让用户选而不是 LLM 猜
  • 把研究 demo 接到工业 backend 是验证路径价值的最佳方式

🚀 技术贡献

  • NL2SQL 歧义 taxonomy（DB + LLM 双源）
  • 多选题驱动消歧 UX 范式
  • Question Rewriting 模块设计
  • 与商业 XiYan-SQL 系统集成

🌍 实践影响

  • 对企业 ChatBI 类产品有直接借鉴：把"猜"换成"问"
  • 启发后续工作（如 Visual Pragmatic Repair, BIRD-INTERACT 评测）
  • 把 NL2SQL 评测从"单步对错"扩展为"含交互的端到端"
  • 降低非技术用户使用 NL2SQL 的不确定感

⚠️ 局限

  • 歧义检测 recall 不是 100%，仍会漏掉部分隐式假设
  • 多选题选项的可穷举性是设计挑战（开放型歧义如"潜力客户"难枚举）
  • 需要与 schema metadata 紧耦合，跨 DB 移植成本不低
  • 用户体验上要平衡"问太多 → 烦" vs "不问 → 错答"
