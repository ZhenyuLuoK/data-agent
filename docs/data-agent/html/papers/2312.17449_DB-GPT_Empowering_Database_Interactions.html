DB-GPT: Empowering Database Interactions with Private Large Language Models

👥 Siqiao Xue, Caigao Jiang, Wenhui Shi, Fangyin Cheng, Keting Chen 等 🏛️ Ant Group / eosphoros-ai 📅 2023.12 (arXiv) · VLDB 2024 demonstration

面向"私有数据 + 私有模型"的开源 LLM-数据库交互框架。核心架构： ① Multi-Sources Knowledge Adaptation（RAG + Fine-tuning 双轨适配企业知识）； ② Service-oriented Multi-model Management Framework (SMMF)（统一管理多种 LLM 部署）； ③ Generative Business Intelligence (GBI)（NL → SQL → 可视化 → 报告）。 是国内最具影响力的开源 LLM × DB 项目（GitHub eosphoros-ai/DB-GPT）。

1. 核心问题与洞察

❌ 企业把 LLM 接到自己 DB 的真实痛点

① 数据隐私不可绕开

企业不能把内部 schema、表数据、业务术语直接发送到外部 LLM API，需要"模型可私有部署"。

② LLM 不懂企业领域知识

通用 LLM 不知道企业内部缩写、业务规则、KPI 定义；纯 prompt few-shot 难以稳定覆盖。

③ 多模型生命周期管理复杂

企业可能同时使用 GPT-4 / 内部 SFT 模型 / 开源 LLM；版本切换、A/B 测试、流量调度缺乏统一框架。

④ NL2SQL 之后的"最后一公里"

SQL 出了结果只是中间品；用户真正要的是图表、解读、可分享的报告。

✅ 核心洞察：把 LLM 视为"数据系统的中间件"

DB-GPT 的核心定位不是某种 NL2SQL 算法，而是一整套把 LLM 工程化嵌入企业数据栈的系统： ① 知识适配层 通过 RAG（向量知识库）+ Text2SQL Fine-tuning（DB-GPT-Hub）双轨补足企业知识； ② SMMF 统一抽象 LLM 调用、调度、监控； ③ Multi-Agent 编排 把 NL → SQL → 可视化 → 解读串成端到端流程； ④ 全栈开源，企业可在自己的机器上完整闭环部署。

逻辑链路

用户 NL 提问 → 📚 知识库 RAG / SFT 模型 → 🔌 SMMF 选模型 → 🤖 Multi-Agent: NL2SQL → 可视化 → 📊 GBI 报告

2. 方法：四大核心模块

① Multi-Sources Knowledge Adaptation

双轨适配企业知识：

  • RAG 路径：把 schema、列描述、业务术语表、SOP 文档切片向量化，查询时检索 top-k 注入 prompt；
  • Fine-tuning 路径：DB-GPT-Hub 提供完整 Text-to-SQL 微调 pipeline（覆盖 BIRD / Spider 与企业自有数据），可在私有数据上训练专用 SQL 模型；
  • 两条路径按场景组合：复杂跨域查询走 RAG，常用查询走 SFT 加速。

② Service-oriented Multi-model Framework (SMMF)

统一抽象 LLM 部署：

  • 支持 OpenAI API / Claude / 国产闭源 / 开源（Llama, ChatGLM, Qwen, InternLM）；
  • 统一接口：load → infer → unload，支持 vLLM / TGI / llama.cpp 等多种 inference engine；
  • 支持 A/B test、流量分配、监控指标统一上报；
  • 核心目的：让上层 Agent 不必关心模型在哪、怎么跑。

③ Multi-Agent 编排

DB-GPT 的 Agent 系统包含多类专精 Agent：

  • DataScientist Agent：数据分析任务编排
  • SQL Agent：NL → SQL（基于 SMMF + RAG schema）
  • Visualization Agent：根据查询结果选图表
  • Summary Agent：生成业务解读

Agent 间通过 GPT-Vis（自研可视化协议）协同输出。

④ Generative Business Intelligence (GBI)

把 NL2SQL 的输出从"一串数据"升级为"一份报告"：

  • SQL 执行结果 → Pandas DataFrame；
  • Visualization Agent 根据数据形态推荐图表（柱状 / 折线 / 饼）；
  • Summary Agent 生成关键发现 + 同环比解读；
  • 支持导出为可分享的 dashboard。
系统视角的贡献：DB-GPT 不追求在 BIRD/Spider 上的 SOTA，而是把 NL2SQL/Data Agent 整套技术栈"开源 + 工程化"，对企业落地更具实用价值。这条工程线由 DB-GPT VLDB 2024 demo paper 进一步深化。

3. 评估方式

作为系统/平台论文，DB-GPT 的评估更偏 能力维度 与 用户场景，而非单一 benchmark 数字。

能力维度（论文 Section 5）

  • 对话式数据库问答（NL2SQL + 多轮）
  • 知识库问答（RAG over 内部文档）
  • 插件 / 工具调用
  • 多模型切换 / 私有部署
  • 端到端 GBI 报告生成

关联评测

  • DB-GPT-Hub：在 Spider / BIRD 上提供完整 SFT pipeline 与 leaderboard，是 LLM Text-to-SQL 微调的事实标准开源组件之一
  • VLDB 2024 demo paper 展示完整产品流程
  • 开源生态：GitHub eosphoros-ai/DB-GPT 是 LLM × DB 方向 star 最多的项目之一

5. 论文展示的代表性场景

基于论文 Section 5（Use Cases）与 VLDB 2024 demo paper 的展示流程。

私有部署的 NL2SQL

企业用户连接内部 MySQL / PostgreSQL，DB-GPT 通过 SMMF 调用本地部署的开源 LLM（如 Qwen / ChatGLM），结合 schema RAG 生成 SQL。整个过程数据不出企业内网。

对比意义：传统 NL2SQL benchmark 论文（DIN-SQL/CHESS）默认用 GPT-4 API，在金融/政府等隐私场景不可用；DB-GPT 把整条链路私有化，是工程上不可替代的形态。

结构化 + 非结构化联合问答

用户问题可能同时涉及 DB 数据（"上季度销售额"）与文档知识（"公司退货政策"）。DB-GPT 通过 Multi-Agent 编排：

  • 路由 Agent 判断需要哪些数据源；
  • SQL Agent 处理结构化部分；
  • Knowledge Agent 处理 RAG 部分；
  • Summary Agent 综合两边给出统一答案。

从问题到可视化报告

用户提问 → SQL Agent 出 SQL → 执行得 DataFrame → Visualization Agent 选合适图表（GPT-Vis 协议）→ Summary Agent 生成业务解读。最终一份"问答 + 图 + 文字洞察"的完整报告。

这是 DB-GPT 把 NL2SQL "变成产品"的关键场景；后续 Vanna、Dataherald 等开源项目也走这条路。

6. 启发与未来方向

💡 设计哲学

  • 私有性是企业级 LLM 的硬约束
  • 多模型管理是平台必备能力，不是奢侈品
  • NL2SQL 本身只是中间环节，要做完整的 NL→Insight
  • 开源闭环是构建生态的最高效方式

🚀 工程贡献

  • SMMF：服务化多模型框架
  • DB-GPT-Hub：Text-to-SQL SFT 标准 pipeline
  • GPT-Vis：Agent ↔ 可视化协议
  • 面向私有 LLM 的端到端开源参考实现

🌍 实践影响

  • 是国内 LLM × DB 方向的事实开源标杆
  • 大量企业基于 DB-GPT 二次开发自有 BI / Data Agent 平台
  • VLDB 2024 demo 把工业系统正式带入数据库顶会视野
  • 对数据 Agent Levels 综述（2602.04261）中"私有部署 + 工程化"维度有直接贡献

⚠️ 局限与未来

  • 本身不深耕 NL2SQL 核心算法（精度依赖底层 LLM 与 SFT 数据质量）
  • 多 Agent 编排相对线性，不像 Data Interpreter 那样动态图
  • Spider 2.0 / 企业级跨多 DB JOIN 场景仍需配合 ReFoRCE / XiYan-SQL 类方法
  • 未来方向：与强 NL2SQL 方法（如 XiYan-SQL）深度集成 + 长 context schema 的更优组织
