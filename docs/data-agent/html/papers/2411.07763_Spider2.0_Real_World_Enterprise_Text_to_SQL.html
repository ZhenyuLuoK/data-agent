Spider 2.0: Evaluating Language Models on Real-World Enterprise Text-to-SQL Workflows

👥 RelationalAI / Univ. of HK / Yale 等多方合作 🏛️ ICLR 2025 Oral 📅 2024.11

1. 研究空白与动机

❌ Spider 1.0 / BIRD 的局限

① Schema 太小

Spider 平均每库不到 10 表；BIRD 略大，但仍远小于真实企业（动辄数百表、数千列）。

② SQL 太短

Spider/BIRD 大多数 SQL 在 ~50 个 token 内；真实企业分析查询常 100~500+ 行，含多层 CTE / window / pivot。

③ 仅 SQLite 单方言

真实数据栈是 Snowflake / BigQuery / Postgres / Redshift 多方言混合，函数与语法差异巨大。

④ 单步生成，无工作流

真实分析师工作流：探索元数据 → 写 SQL → 校验 → 调试 → 整合到 dbt 模型。Spider 1.0 完全没有这些。

✅ Spider 2.0 的核心贡献

① 632 个真实企业级文本-到-SQL 工作流任务，从开源项目、社区案例、真实数据栈中采集；
② 多方言（BigQuery / Snowflake / DuckDB / SQLite / Postgres）覆盖；
③ 三个评测层：Spider2.0 / Spider2.0-Lite（简化版）/ Spider2.0-Snow；
④ 任务包含 schema 探索 + 多文件 + dbt 编排，要求 agentic 解决而非单次 prompt；
⑤ 实证揭示同等模型在 Spider 2.0（agent，最佳 21.3%）vs Spider 1.0（>85%）上的巨大差距，是 NL2SQL 真实差距的诚实尺子。

逻辑链路

Spider 1.0 / BIRD（学术 schema） → 真实企业差距 → Spider 2.0：真工作流 + 多方言 → Agentic 评测 → 揭示 LLM 大缺口

2. Benchmark 构建流水线

① 任务源头

  • 开源 dbt 项目仓库（公开 repo）
  • BigQuery / Snowflake 公开示例数据集
  • Stack Overflow 上的真实 SQL 问题
  • 社区分析平台案例

② 标注与质量控制

  • 由资深数据工程师改写为自然语言任务
  • 提供 ground-truth SQL + 期望表/列输出
  • 多人交叉审校，确保任务可解
  • 每个任务附"上下文文件"（schema dump、dbt 配置等）

③ 三个评测层

  • Spider 2.0：完整 agentic 任务，需多步执行
  • Spider 2.0-Lite：简化版，单 SQL 完成
  • Spider 2.0-Snow：Snowflake 单方言专项

④ 评分指标

  • SQL 执行结果匹配（行级 / 集合级）
  • 容忍列序、行序差异
  • 对 dbt 任务允许多步生成与文件修改
构建哲学：拒绝合成数据。所有任务必须是真实工程师真的写过的。这让 Spider 2.0 成为"现实主义 benchmark"的旗帜。

3. 评估框架

评估对象

  • 闭源：GPT-4 / GPT-4o / Claude-3 系列
  • 开源：Llama-3、Code-Llama、DeepSeek-Coder
  • Agent 框架：ReAct、CodeAct 等

评测条件

  • 提供 schema 文件 + 工作目录 + 数据库连接
  • 允许多步推理 / 工具调用 / 执行反馈
  • 限制最大轮数（agent 预算）

数据来源：Spider 2.0 论文（arXiv:2411.07763，ICLR 2025）+ 官方 leaderboard。论文明确说明 GPT-4-based agent 仅能解决 21.3% 的 Spider 2.0 任务（"a success rate of only 21.3%"），远低于 Spider 1.0。

关键实证发现

  • 同模型代际差：相同 LLM 在 Spider 1.0 上接近饱和（>85%），到 Spider 2.0 上骤降。
  • 方法迁移失败：经典 prompt-based 方法直接套用到 Spider 2.0-Snow 上几乎完全失效（第三方 reproduction：DAIL-SQL+GPT-4o = 2.20%、CHESS+GPT-4o = 1.28%、SGU-SQL+GPT-4o = 4.39%）。
  • 方言敏感：BigQuery / Snowflake / DuckDB 之间的函数差异（UNNEST / QUALIFY / WITHIN GROUP 等）是错误高发区。
  • Agent 路线收益明显：能主动探索 schema、读取元数据、迭代调试的 agent 显著超过单次 prompt 方法。
  • dbt 子集（68 题）几乎全员翻车：跨文件协同 + 工程语义，对当前 LLM agent 是显著未解决问题。

5. 任务类型剖析（基于论文结构）

注：以下为论文中定义的三种主要任务形态，描述基于 Spider 2.0 论文 Section 2/3 与 GitHub 仓库说明，不展示具体测试题以避免泄题。

完整 Agent 工作流

提供：自然语言任务描述 + 一个工作目录（含 schema 文件、元数据文件、有时附 sample 数据）+ 数据库连接。

Agent 能力要求：

  • 主动探索元数据（如读 INFORMATION_SCHEMA、列出表、抽样数据）
  • 多步生成 + 多步执行 + 错误反馈
  • 最终产出可执行的、答案正确的 SQL 或多 SQL 序列

论文实测：GPT-4-based agent 仅 21.3% 任务成功，最强 baseline 也大量失败在 schema 探索阶段。

简化的 Text-to-SQL 子集

论文为方便 NL2SQL 社区直接对比，提供：

  • Spider 2.0-Lite：547 题，covering BigQuery / Snowflake / SQLite 等多平台，单次 SQL 形式
  • Spider 2.0-Snow：547 题，仅 Snowflake 单方言

实测对比（第三方 benchmarking）：DAIL-SQL+GPT-4o 在 Spider 2.0-Snow 仅 2.20%、CHESS+GPT-4o 1.28%、SGU-SQL+GPT-4o 4.39%；后续专门工作 ReFoRCE 在 Snow 达 31.26%、Lite 达 30.35%；最强模型在 Snow 上 peak 也只到 59%，距 Spider 1.0 接近饱和的 SOTA 差距巨大。

dbt Code Agent 任务

共 68 题，要求 agent 在已有 dbt 项目中：

  • 新增 / 修改 SQL 模型文件
  • 声明 {{ ref(...) }} 依赖、schema.yml 描述与测试
  • 触发 dbt run 验证

这是 Spider 2.0 中最难的子集，揭示了 LLM agent 在多文件协同的工程化任务上能力远未达标。

6. 启发与未来方向

💡 Benchmark 设计哲学

  • 真实工作流 > 合成数据
  • 多方言强制：让评测反映真实数据栈
  • Agentic 评测：单 SQL 准确率不再够用
  • 多层难度：Lite / Snow / Full 满足不同研究群体

🚀 对学界与业界的影响

  • 2024-2025 多个工作专门"刷 Spider 2.0"
  • 从此 NL2SQL 论文必报 Spider 2.0 数字
  • 推动了"agent + tool + schema 探索"路线

🌍 实践影响

  • 企业落地 NL2SQL 时的"现实期望校准"工具
  • 给"端到端 SQL agent"的能力上限画了基线

⚠️ 局限

  • 覆盖的真实数据栈仍以英文为主
  • 开源场景限制 → 没有真正的"商业敏感"schema
  • 评分基于执行结果，对"等价 SQL 但写法不同"宽松，但对"业务正确但行序差异"也可能误判
