1. 核心问题与洞察

❌ 当时方法的混乱

2023 年中，"用 LLM 做 Text-to-SQL"已被 OpenAI Demo、ChatGPT-SQL、Codex、C3-SQL 等多种方法实现，但这些工作有如下问题：

① Prompt 风格参差不齐

有的用 NL 描述 schema，有的用 CREATE 语句，有的用类 markdown 表格，缺乏受控对比。

② 示例选择"凭感觉"

没人系统比较过"按问题相似度选 vs. 按 SQL 相似度选" 哪个真的更好。

③ Few-shot 中是否给 SQL？

有的工作只给问题不给 SQL，有的两者都给，无定论。

④ Token 经济性被忽视

大 schema 让 prompt 动辄数万 token，但很少有人讨论"在等准确率前提下 token 最少的设计"。

✅ 核心洞察：把 prompt 设计形式化为 4 个正交维度

论文用 "工程实证 + 控制变量" 的方法，把"最优 prompt 怎么写"变成可被科学回答的问题：

  • 固定 LLM、固定 schema、固定 benchmark；
  • 每次只变一个维度（如示例选择策略），跑全集；
  • 得到全局最优组合 = DAIL-SQL。
问题表示 (Q-Repr) ⊗ 示例选择 (Selection) ⊗ 示例组织 (Organization) ⊗ 提示组件 (Components) → 最优组合 = DAIL-SQL

2. 方法：四维度系统评估

5 种问题表示

  • Basic Prompt (BSP)：自然语言描述 schema + 问题
  • Text Representation (TR)：在 BSP 上加规则提示
  • OpenAI Demo (OD)：OpenAI 官方文档示例风格
  • Code Representation (CR) ⭐：用 SQL CREATE TABLE 语句作为 schema 表示
  • Alpaca SFT Prompt (AS)：指令式 SFT 模板

实验显示 CR 一骑绝尘：因为 GPT-4 训练数据中存在大量 CREATE 语句 + SELECT 模式，"用 SQL 解释 SQL"是最自然的对齐方式。

/* Code Representation 风格 */
CREATE TABLE singer (
    singer_id INT PRIMARY KEY,
    name VARCHAR(50),
    country VARCHAR(50),
    age INT
);
CREATE TABLE song (
    song_id INT PRIMARY KEY,
    singer_id INT REFERENCES singer(singer_id),
    title VARCHAR(100)
);
-- 问题: How many singers from France are older than 30?
SELECT

4 种示例选择策略

  1. Random：从训练集随机抽 k 个
  2. Question Similarity (QS)：用 sentence-BERT 取问题最相近的 k 个
  3. Masked Question Similarity (MQS)：先把领域词 mask 掉再算相似度
  4. Query Similarity (DAIL Selection) ⭐：用预生成的 SQL skeleton计算相似度（如 SELECT _ FROM _ WHERE _ GROUP BY _）

关键发现：SQL skeleton 相似度 > 问题相似度 > 随机。"问题表面相似但 SQL 结构不同"反而是误导性示例（如两道都问 "how many" 但一道是 COUNT，一道是 SUM）。

2 种示例组织方式

  • Full-Information Organization (FI)：每个示例都给 schema + 问题 + SQL
  • SQL-Only Organization (SO)：只给 问题 + SQL，schema 在 prompt 头部一次性出现

论文证明 FI > SO：每个示例都带自己的 schema，能让 LLM 学到"如何把 schema 与 SQL 关联"，而不仅仅是"如何把问题映射到 SQL 模板"。

DAIL-SQL = 全局最优组合

问题表示:    Code Representation (CR)
示例选择:    Query Similarity (基于 SQL skeleton)
示例组织:    Full-Information (每例完整 schema+问题+SQL)
提示组件:    + 显式注释关键约束 (如 PK/FK)
LLM:        GPT-4
Few-shot:   k=5 ~ 9

这一组合最终在 Spider 测试集达到 86.6% EX，超过此前所有 ICL/FT 方法。

方法论价值：DAIL-SQL 不是"提出新算法"，而是"系统化回答了一系列工程问题"。在 LLM 时代，这种"严谨控制变量的 prompt 实证研究"本身就是稀缺的科学贡献。

3. 评估框架

评测设置

  • Benchmark：Spider, Spider-SYN, Spider-Realistic, BIRD
  • LLM：GPT-4, GPT-3.5-turbo, Vicuna-33B, LLaMA-70B
  • 每个维度独立 grid search，跑完全部 5 × 4 × 2 = 40 组合

评测指标

  • EX (Execution Accuracy)
  • EM (Exact Match)
  • VES (Valid Efficiency Score, BIRD)
  • Token 消耗（首份系统化 token 经济性分析）

开源 LLM 表现（论文 Section 5）

论文还在 Vicuna-33B、LLaMA-2、CodeLlama 等开源 LLM 上重复实验。综合定性结论：

  • 开源 LLM 整体显著落后于 GPT-4，验证 ICL 路线对底座 LLM 能力有强依赖；
  • 同样 prompt 设置下，code-tuned LLM（如 CodeLlama）通常优于 chat-tuned 同尺寸模型；
  • 更大尺寸 / 更新版本的开源模型可以缩短与 GPT-4 的差距，但当时未消除。

具体逐模型 EX 数字详见 DAIL-SQL 论文 Table 7（不同开源 LLM × 不同 prompt 设置）。

5. 案例研究

表示风格的 5 种对比（论文 Section 3）

DAIL-SQL 系统比较了 5 种 schema/问题表示：Basic、Text Representation、OpenAI Demonstration、Code Representation (CR)、Alpaca SFT。论文 Table 2 给出每种风格在 GPT-4 下的 EX。

定性结论：

  • Code Representation（CR）最优：用 CREATE TABLE 文本表示 schema、把问题作为 SQL 注释；与 LLM 训练分布更一致。
  • Basic / 自然语言风格：让 LLM 在 schema 描述与 SQL 生成之间做隐式翻译，比 CR 准确率明显更低。
  • OpenAI Demonstration 风格：介于二者之间。

这是首批系统化论证"用 SQL 解释 SQL"显著优于"用自然语言解释 SQL"的实验性工作之一。

SQL skeleton 选例的优势（论文 Section 4）

DAIL-SQL 比较了 4 种 example selection 策略：

  • Random：随机选 few-shot
  • Question Similarity (QS)：基于问题文本嵌入相似度
  • Masked Question Similarity (MQS)：把字面常量 mask 后再算相似度
  • DAIL Selection：先用 base prompt 预生成 SQL skeleton，再按 SQL skeleton 相似度选例

论文 Table 3 实证：DAIL Selection > MQS > QS > Random。原因是问题文本相似不代表 SQL 结构相似（"how many books"和"how many cars"问法相似但 SQL skeleton 可能完全不同），结构相似才是 ICL 真正受益的相似。这一发现也被 MAC-SQL 等后续工作沿用。

Token 经济性

论文专门用一节讨论 token 消耗：相比逐步 CoT 一次输出 7-8K token 的做法，DAIL-SQL 选择 SQL-Only Organization + 最少必要 schema，在保持高准确率前提下显著降低 token 数，论文指出这是它能在 GPT-4 高 API 成本下落地的关键工程优势。

注：论文未公布精确平均 token 数，但讨论了不同 prompt 组件的 token 占比及对成本的影响。

6. 启发与未来方向

💡 设计哲学

  • 用 SQL 解释 SQL：CR 表示利用了 LLM 训练分布
  • 结构相似 > 语义相似：选例时 SQL skeleton 比问题文本更有效
  • Full-Info 让 LLM 学到映射，不是模板

🚀 技术贡献

  • 首份 LLM-based NL2SQL 的 prompt benchmark
  • 提出 SQL-skeleton-based example selection（被 DIN-SQL/MAC-SQL 复用）
  • 开源代码 + 全部 prompt 模板

🌍 影响

  • VLDB 2024 收录
  • 成为后续 NL2SQL 论文标准基线
  • 多家开源 SQL Agent（LangChain SQL Agent, LlamaIndex）默认 prompt 风格借鉴 CR

⚠️ 局限

  • 纯 prompt 路线在 BIRD 上很快被多 Agent 方法超越
  • 无 schema linking 模块 → 大型 schema 失效
  • 无 self-correction → 错误一次定终身
  • 未触及交互、歧义、效率维度
